## 1. The complete finite workflow

An authorized staff member saves the existing Charity Incubator's native JSON, deliberately opens it in the shared OS, selects **one saved project and one saved milestone**, reads the complete selected source/context, chooses an existing accessible OS program and explicitly declares the milestone→project relationship. They author two target titles and completion conditions. An exact preview shows two new ordinary Projects records: one `kind:project`, one `kind:milestone` with `projectId` equal to the freshly generated project ID. Both start `planned`, owned by the acting member, revision 1, with no approval, snapshot, integration source or dependencies.

Commit is atomic and supports exact Retry after a lost response. Retained selected source versions explain what was copied; later ordinary editing remains available. A newly chosen file can explicitly refresh the selected source and create a separately reviewed new pair; it never overwrites the existing pair. An administrator's whole-workspace restore retains provenance as inactive history. Explicit adoption can create a new pair under current authority; it never reactivates an imported command.

This is a planning bridge. A source label such as “Accepted locally,” “Learning,” “Hand-off” or “Closed” never determines OS status or an independently observed result. No source owner/role/authority/consent prose becomes an account, membership, staff assignment, authorization, contact, consent, payment, event, participant, grant, credential or scientific evidence. The ordinary Projects workflow and its normal approval policy remain unchanged. Do not impose Learning's approved-program/causal-evidence requirement on ordinary planned drafts.

# Guarded donor-tool recovery

Pre-implementation plan · October 27, 2026 · AI-assisted · review: draft. Read the [exact interfaces](DONOR_RECOVERY_INTERFACES.md). This plan authorizes no runtime, browser, provider, data migration or publication change by itself.

## Useful outcome

An older donor/funder tool should keep a valid saved record, a failed-write draft and an unreadable saved copy distinct. A person can save a change, see whether it persisted, export the right copy, review a replacement and recover without silently replacing another updated tab's work. This completes the bounded engineering work in [D1](MEGA_LIST_ACCEPTANCE.md). It does not move money, send a message, rate a charity, produce legal advice or establish shared organizational authority.

Keep every existing key and readable value shape. Do not add version fields to those values, reinterpret earlier unknowns, rewrite an old key during load or scan other tools' storage. Add a namespaced D1 cell and asynchronous tool facade. Reuse the tested L1 algorithm as a design reference, not the released helper itself: D1 needs explicit `hasState` and `hasUndo` flags because null can be a valid value or fallback. Null cannot be the cell's internal sentinel for unavailable state or absent undo. No L1, R2, R3, W1, OS or publication key/helper changes belong in this slice.

## Actual boundary and current gaps

The existing [donor checker](../scripts/check-donor-records.mjs) passes ten groups: gift missingness and round trips, sequential synthetic storage cases, capacity and strict compilation of twelve actual tool scripts. That does not mount their recovery controls or establish browser acceptance.

A bounded actual-module probe with synthetic DOM/storage reproduced these current defects in [durable-store.ts](../src/lib/client/durable-store.ts):

- A delayed valid file A can finish after invalid file B and re-enable A's old Apply control.
- The control labeled protected saved copy rereads current storage; initial corrupt A is not separately offered after unseen B appears.
- A foreign write before preview can silently become the preview's baseline, without a first external-change warning.
- Compare and set are separate operations without a shared Web Lock. A controlled scheduling probe demonstrates the gap; it does not prove a particular native browser interleaving.

The lock guarantee must stay precise. Web Locks serialize **cooperating updated tabs using the same exact lock**. A direct localStorage write, older cached client or another implementation that ignores that lock can still write between a check and a set. localStorage has no compare-and-swap transaction. Tests must prove shared lock use and final checks, rather than claim universal protection from arbitrary JavaScript. Where useful, advise reloading older open tool tabs after the release.

## Async integration is part of the fix

The old `save` returns an immediate boolean. A Web Lock requires an asynchronous operation. Every affected initializer, load/save/remove handler, timer, native importer, undo/delete/reset and recovery action must adopt the new facade together. Returning a Promise through the old boolean API would make failed saves appear successful.

Initialize and validate before enabling saved-state mutation. Read the resulting snapshot to hydrate once; a late initialization may not overwrite new form input. The tool keeps its own detached working copy rather than mutating a store-owned object. Every relevant input, reset, imported selection, source/record switch and destructive action advances its form generation. Native import/restore file choices have a separate generation and invalidate old authority immediately.

Capture a full candidate synchronously, before the first await. The facade owns a detached copy and queues it. A later form generation supersedes an unstarted capture. At the queue head, prepare against the current valid memory after earlier own operations have settled; this is a new full replacement, not replay of a command. A foreign disk change blocks the queue and never triggers automatic adoption or rebase. The final generation/disk checks happen under the lock immediately before mutation.

The facade and recovery controls share one opaque view tracker created by the D1 module. It owns primitive form/recovery generations and dirty flags. The store reads its private state directly; no caller observer callback runs under a lock. No public callback receives a held lock or an internal cell. Operation results are handled after locks are released; a forged tracker or record does not grant recovery authority.

After awaiting, do not reset/fill a newer form or announce that its latest input was saved. If an older candidate persisted and later input exists, say the earlier saved record is kept and later edits remain in this tab. A failed valid write stays in memory with retry/export and an unload warning. Retry uses the exact candidate and intended set/remove operation; it does not rerun submit/import, regenerate IDs/timestamps or repeat a delete command.

Each tool must show these distinct states: unsubmitted raw HTML input; a validated queued replacement; valid unsaved memory after a write failure; and actually saved state. The generic backup includes the valid store value, not arbitrary DOM input. Existing native per-tool exports may include more or less; label their actual scope. Do not silently save a CE calculation merely to claim full-form recovery. Measurement's delayed save needs a warning while input is pending; an async `pagehide` callback cannot guarantee the last write finishes.

## Cell, admission and recovery

- Full storage key and lock name match exactly, such as `charitology.gifts`. Every cooperating write, retry, remove, restore, clear, undo and reload/adoption uses that lock. Keep exact observed saved strings separate from current valid memory. Check both memory generation/hash and exact observed disk bytes under the lock.
- Unsupported Web Locks, secure-context hashing or lock acquisition means no write/remove/restore/undo fallback. Valid readable data and recovery remain available. Calculations can still work locally with an honest saving-unavailable notice.
- Explicit flags distinguish valid null, absent saved key, corrupt saved data, unreadable storage, an empty array and no undo. A corrupt initial key must not look like a blank saved workspace. Read exceptions mean observed bytes are unavailable, not absent.
- Keep the original protected raw copy and latest observed raw copy separately. Every newly read foreign B or C causes a first warning and preview refusal, even when already blocked by corrupt A. A subsequent fresh explicit preview may bind that exact observed copy. Retain valid current memory too. This does not promise an archive of every external intermediate version.
- Owned, deeply frozen, one-use previews are recognized privately. A copied JSON object, matching hash, different store instance or changed caller object cannot authorize replacement/removal. All arguments/options are detached or captured before awaiting and checked again at required boundaries.
- A file choice immediately removes prior Apply/Clear and invalidates old reads. Bound actual owned bytes before decoding, use fatal UTF-8, a 30-second deadline, duplicate-key refusal and maximum JSON container depth 32. Late A cannot reauthorize an action after B, clear, reload, undo, input change, dispose or a foreign save.
- A whole individual backup, including the pretty v1 envelope, is at most **8,000,000 UTF-8 bytes**, preserving the existing serializer's no-terminal-newline convention. Keep compatible `charitology-local-draft` v1 exports/imports and old JSON value shapes. Validate before assignment; reject oversize as a whole. No trimming, defaulting, ID regeneration or unknown-to-zero conversion.
- Per-tool validators stay semantic and deterministic. Existing cleaners may be used only to detect incompatible input, not silently normalize it. Unknown future fields are refused or explicitly retained outside active data with a compatibility warning; none are silently discarded. Shared portfolio validation must agree in Builder and Split. Preserve optional-field compatibility deliberately, including historically omitted undefined object fields; do not change array meaning.
- Production opens the fixed canonical key registry; callers cannot supply weaker validators, generic shape fallbacks or alias registration. Only grant-draft admits saved JSON null. Other nullable load fallbacks do not make null a valid saved record. Preserve the actual Portfolio producer's tilt range −100 to 100, correcting the old narrower saved-state validator rather than dropping negative-tilt records. CE raw string fields remain bounded by the full backup, not invented per-field limits.
- A value-save no-op means the exact readable observed saved baseline already represents that value, persistence is saved and unsaved is false. Memory equality alone is insufficient. Saving an absent-key default or re-saving a failed-write candidate must attempt persistence or remain visibly unsaved, never report a Saved no-op.
- Raw recovery uses a lossless JSON wrapper around the exact JavaScript string, preserving unpaired UTF-16 through escapes. Its complete wrapper has a separate 64,000,000 UTF-8-byte bound; refuse visibly above that bound and never truncate. A plain text option requires exact UTF-8 encode/decode equality. An oversize corrupt archive is labeled as recovery material, not a normal restorable backup.
- Successful reload clears old undo/preview authority. Clear removes only the selected key after explicit preview/confirmation. Failed set/remove retains valid memory, the old saved bytes and an exact retry operation. Generated Blob requests are not proof that a native file was saved.

## Three-key grant recovery

Keep the three existing key values unchanged. Provide individual backups plus one complete private bundle. The complete bundle has exactly proposal library, weights and current draft, preserving absence separately from a value or valid unsaved-memory candidate. Every individual whole wrapper must fit 8,000,000 bytes; the complete pretty bundle must fit **24,008,192 bytes**. The whole bundle cap wins. If it refuses, offer valid individual backups; never truncate or quietly drop a member.

The dedicated grant coordinator privately owns all three cells. Any operation inspecting their relationships acquires locks in lexical order: `charitology.grant-draft`, `charitology.grant-proposals`, `charitology.grant-weights`. It never calls a public cell method that reacquires a held lock. Only its private unforgeable lease may call the internal lock-free guarded primitives. No public `withLocks(callback)` API exists.

A normal Save proposal may need library and draft writes. Validate and retain all intended candidates first, then write in the defined library → weights → draft order, stopping on failure. Return per-member outcomes and retain the exact remaining candidates. If the library saved and the draft failed, say so. Do not claim atomicity, erase the pending candidate or automatically roll back foreign state.

A bundle restore is deliberately **separate explicit member steps**, library → weights → draft. Preview validates the complete bundle and draft/library relationship before any write, then displays all source members and differences. Each member receives a fresh owned step preview and explicit confirmation. Under all three locks, recheck the exact observed vector, current memory and UI generation, then mutate only that member. Known successful steps update the vector; another tab's change invalidates the rest of the plan.

A complete source can temporarily leave the old saved draft referring to a different library between steps. That is a visible partial recovery state, not permission to clean the old draft ID. While such a plan/pending set exists, disable normal grant edits and keep recovery/export/retry available. After reload, detect an orphan draft/library relationship, retain all exact values and show a repair notice. An individual library restore that would orphan the current draft is refused; the complete owned plan can make its explicitly reviewed transition one member at a time. A consistent mixture after a restart still cannot be called a completed source-bundle restore without a fresh comparison against that source file.

An initially inconsistent target must not become stuck: accept a valid complete source plan, or offer explicit removal of the current draft key after its recovery warning. Neither path cleans an ID silently. Keep a complete pending **desired** vector export available, including future validated source members not yet applied, and distinguish it from the current saved/working vector. Exporting a desired bundle authorizes no later step.

If step two fails, step one remains visibly applied and step three is not attempted. Preserve all source members and current/original memory for export, show partial completion and warn before leaving. Retry only the exact failed candidate against unchanged baselines. After reload, selecting the same bundle again can compare every member and deliberately resume; no hidden journal or automatic resume exists. Do not say the complete workspace is restored until a final fresh locked comparison confirms all desired members match. Unreadable members prevent a valid complete-bundle claim; offer their raw copies and the valid members individually.

## Acceptance and release gates

The implementation must add meaningful actual-module checks, not merely mirror the new functions:

1. Exact-key schemas, readable old fixtures, null/0/false/blank distinctions, IDs and dates, shared portfolio compatibility including negative tilt, duplicate/depth/UTF-8 admission, lossless raw UTF-16, exact old no-newline 8,000,000-byte individual wrapper and +1 refusal, grant whole-bundle boundary, absent-default and failed-memory-equal no-op cases.
2. Two cooperating lock contenders using exact final lock names; foreign-before-commit refusal; stale edit/delete/import/undo/remove; read/set/remove/lock failures; exact failed retry; caller/options mutation while queued; copied/foreign/reused authority; no other-key writes.
3. Actual mounted recovery controls with controlled file-read scheduling: A → invalid B, old read after clear/reload/undo/command, timeout, initial corrupt A → unseen B → C, before/after-preview foreign writes, stale Apply, unsupported capability, quota indicator, explicit key-only clear and Blob bytes.
4. All twelve real Astro scripts: actual save trigger, each available delete/import/undo, post-await newer-form retention, visible failure state and honest native-output versus record-backup scope. Static checks refuse unawaited/bypassed target-key writes. Strict TypeScript remains clean.
5. Grant complete export and sequential restore: absence/null, full cap, exact order/vector, library success plus weights failure, no automatic draft attempt, exported pending candidates, exact retry, foreign change refusal, reload/review resume and no false full-success message.
6. Later controlled Chrome on a fresh private localhost origin: synthetic fictional fixtures only, all nine routes and three auxiliary compatibility mounts, two tabs, native FileChooser, stale restore, quota/corruption controls, keyboard/focus and 320/390 light/dark. Root grants Chrome and freezes the build first. No provider, donation link, send, account, actual private recipient, user-origin key discovery or global browser setting change.

A private fault-injection harness can serve copies of the actual final pages/assets on a new origin with a clearly labeled control page. It may seed only the allowlisted fictional keys and expose generated Blob bytes. Distinguish that injected failure evidence from normal browser use, mounted synthetic DOM from a real browser, and generated files from native saved-file proof. Existing locked-Mac limitations stay explicit.

Root commits this plan/interface freeze before implementation and assigns nonoverlapping store, schema and UI owners. Later build/CI/browser/publication evidence belongs in an acceptance record. This plan alone supplies none of it.

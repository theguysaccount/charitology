# Local program graph: implementation and acceptance

October 27, 2026 · AI-assisted · review: draft · **Local/browser/runtime CI acceptance passed; publication pending.**

The companion notebook connects selected saved records from nine program workspaces. Capture a complete source copy, choose the records to track, connect plans and evidence notes, inspect either direction of a relationship, then refresh the source and review what changed. It keeps the original editors, keys and version-1 exports separate. It records local snapshots and explanations; it does not grant shared permission, independent review, funding or observed results.

The [public plan](PROGRAM_GRAPH_PLAN.md) and [interfaces](PROGRAM_GRAPH_INTERFACES.md) were committed as `7c46a1be56713597d49b9429f402ec95a56b3877` before runtime. Runtime `68d3f4617315414d0b76bef14861b75eae96b599` contains the tested implementation. [PR #18](https://github.com/theguysaccount/charitology/pull/18) tracks implementation and release. This is the bounded local relationship part of W1; the authenticated shared OS and its local-to-shared migration remain separate systems.

## Working flow

1. Open any of the nine partner-program pages. Deliberately preview that page’s saved workspace, or select a complete version-1 JSON file and its program. No source key is read automatically or discovered by scanning storage.
2. Enroll a named source instance or explicitly refresh a known one. The preview shows context, row inventory, changed or missing tracked records and overlaps. A separate overlapping copy requires an acknowledgement; matching titles or legacy IDs never merge instances.
3. Select new records to retain. Existing tracked records always refresh. Every source field and row is validated, including unselected rows. Source bytes and unselected values are discarded after a successful capture; their hashes cannot reconstruct the original file. The retained complete ID inventory and context can themselves contain private text.
4. Connect records with one of six descriptive relationships. Review the exact endpoint versions and explanation. An existing free-text reference may be retained as provenance without claiming external reconciliation. Dependency cycles and duplicate active relationships are refused.
5. Refresh when a source changes. Renamed or changed fields append versions and make affected relationships stale. Missing records retain their earlier values and make relationships unresolved. A missing ID that returns needs an explicit identity acknowledgement before a new relationship review; later title changes cannot erase this warning. Retired sources and links keep their history. Resuming a source requires a fresh complete capture.
6. Export a complete graph backup or a deliberately selected CSV/Markdown packet. Selected packets include their endpoints, necessary reviewed history and context; they exclude unrelated graph records, complete inventories and raw forms. They cannot restore the graph. The complete JSON includes all retained graph records, histories, source inventories, context and the saved unfinished form, including work not selected for a packet.

Current means reviewed against the latest accepted **copies**, not synchronization with the original workspaces. Renaming a source changes its current display alias; no historical alias or source-lifecycle event log is promised. No title matching, money rollup, cause score or inferred operational approval is supplied.

## Compatibility and recovery

The inert adapters preserve nine actual version-1 program definitions, 46 collections and 381 fields including context. Complete known source exports retain exact accepted strings while temporary trimmed values are used only for validation. Unknown fields, missing configured strings, duplicate decoded JSON keys, unsupported versions, malformed UTF-8, moved record IDs and excessive nesting fail before a partial graph can be accepted.

The graph uses only `charitology.program-graph.v1` and the same-named Web Lock. The source keys and formats remain unchanged. Saved-byte comparison and a separate memory generation protect commits, retries, restore, clear, undo and reload. Corrupt or unreadable initial storage is unavailable rather than an invented empty graph. Readable protected bytes have a raw recovery download; a valid replacement requires a fresh deliberate preview. A failed write retains an exportable valid memory candidate and retries that candidate without replaying its command.

Mutable queued prepared objects are detached and stamped before waiting for a lock, then rechecked through validation and no-op paths. A queued reload cannot gain discard authority from a later edit to its options. These checks were verified with actual-module regressions and independently reproduced fixes.

Raw forms retain their exact target and version bindings, including malformed fields. A failed/no-op command, changed source preview or newer form cannot silently clear them. Discarding a form in this tab and explicitly saving the discarded state have different labels; failed persistence never claims the saved form was removed. A full backup that cannot fit a newer raw form leaves plain raw-form recovery available. Uncommitted source file bytes are not part of a graph backup and retain their own leaving-page warning until captured or deliberately discarded.

Browser-origin storage is accessible to this site’s scripts and people using the browser. It is not encrypted confidential case storage. No graph data is uploaded, no evidence URL is fetched and no provider or shared OS record is created by this feature.

## Bounds

- 20 source instances, 100 captures, 500 nodes, 2,000 retained node versions, 500 links and 2,000 retained link versions. Missing and retired history counts.
- Complete pretty JSON backup, including wrapper and newline: 2,097,152 UTF-8 bytes. The exact boundary round-trips through the actual model and store; a valid-checksum one-byte excess is refused without replacing memory or saved bytes.
- Original complete source file: 8,000,000 bytes, 250 rows per collection and 500 total, with the unchanged field limits. Strict JSON container depth is at most 32.
- Raw form: 40 combined binding/field keys, 16,384 characters per value and 512 KiB canonical draft, also subject to the complete backup bound.
- Lists page 25 records. Connected work shows at most two hops and 200 nodes, with an explicit view-truncation notice; stored data and exports are not silently truncated.

# Grant-to-report implementation plan

Frozen before implementation · October 26, 2026 · review: draft · AI-assisted planning

Baseline inspected: `3913166b8e3be5f301d4145944e05fe1e76eef42`. This contract defines a bounded implementation of O2 in the [acceptance register](MEGA_LIST_ACCEPTANCE.md). The planning checkpoint changes no runtime, database, account, configuration or delivery state. The following product choices are frozen for this implementation. Application files match the published delivery runtime; planning starts from merged main `fc6be0026c246b3d22cce89b7874583cfa7086e6`.

## Proposed outcome

An authorized team prepares one report for **one explicit grant agreement, one program and one date period**. The team selects dated financial references and outcome observations in an ordinary Reporting record. A different authorized contributor approves that exact manifest. The server previews a source-derived report, then freezes the reviewed version after checking that every required source and permission is still current.

The output explains what was awarded, what external records say was received or spent, what was measured, what remains unknown and which approved source revision supports each field or calculation. A board reader receives only an approved, scoped report projection. A later correction produces a new immutable edition with a reason and a link to the earlier report.

This is a reporting aid. It does not submit an application, transfer money, replace a ledger, reconcile a bank, issue a tax receipt, certify accounts, verify causal impact or establish that a real person reviewed synthetic acceptance data. A stored software approval means an authorized second account approved a record; it is not professional accreditation or independent verification of its contents.

## Chosen first-slice behavior

1. **One agreement and one program per report.** Require an approved agreement whose `programId` is explicit. Its submitted application and the selected manifest must belong to the same program. Do not widen generic `inScope`; apply the stricter rule only to this assembler. Multi-program agreements require a later allocation design.
2. **Use Reporting as the manifest.** Its approved `agreementId`, `startDate`, `endDate`, `financeIds`, new `receiptIds`, `outcomeIds`, summary, missingness and audience are the selection. An explicit nullable `assemblyMethod=grant-report-v1` and a 64-hex `sourceDigest` identify the new contract. Prepare computes that compact digest from exact sources before ordinary manifest approval. A preview cannot add unapproved narrative or arbitrary record IDs. Zero selected observations is allowed and visibly says none were selected; it never means zero outcomes.
3. **Reuse explicit gift references for receipts.** Add Fundraising `agreementId` and Reporting `receiptIds`. Only selected, currently approved `kind=gift-reference` rows with the exact agreement/program, `receivedDate`, `receiptReference` and an identified external system enter receipt calculations. Pledges/campaigns/acknowledgments do not. For optional period spending totals, add nullable Finance `actualClass: unknown | cash-spent | other` and `actualDate`; only explicit approved cash-spent actual-reference rows with external identity qualify. Existing Finance actuals remain unclassified, never cash received. These are externally referenced assertions, not bank/payment proof.
4. **Do not pool outcome observations.** First slice presents each observation with its indicator, exact unit, period, value, denominator, source and caveat. It may group identical indicator/unit pairs for reading, but does not sum people, average rates, pool denominators or calculate cost per outcome. This avoids inventing compatible populations or an additive measurement model.
5. **Authenticated board view only.** A manifest intended for the board creates a deliberately limited board projection. A funder/private manifest is staff-readable and downloadable; no external-funder identity mechanism or anonymous publication is added. `visibility=public` is rejected for this new assembler with a clear explanation. The generic Reporting record stays private as today.
6. **JSON plus a readable, printable client view.** Freeze one canonical JSON payload and a precomputed board projection. Render them with text nodes; provide print CSS. Do not introduce a PDF service, server HTML template engine, spreadsheet formulas or external document fetches.
7. **Corrections append.** Add optional `supersedesReportId` and required `revisionReason` to the Reporting manifest when replacing a grant report. Its independent approval binds the reason. Freeze a new report; never mutate or delete the old one. “Superseded” is a derived relationship, not an update to the old row.

## Complete bounded workflow

1. **Record the chain.** Opportunity → versioned application → independent approval → submitted snapshot/reference → explicit grant agreement/period/restriction. Use existing modules and workflow commands. A recorded decision/award does not establish receipt. No workflow stage is advanced implicitly by the report assembler.
2. **Plan and track work.** Link restricted budgets/allocations to the agreement using existing Finance fields. Continue to use Projects/tasks for deadlines. The first report does not import arbitrary task prose or task-owner identities. Task completion can be inspected separately; it is not evidence that grant conditions were met. Grant-specific task linkage is a useful later extension, not a prerequisite for accurate financial/measurement output.
3. **Record dated evidence.** Link gift-reference receipts explicitly to the agreement; add explicit spending-reference rows and indicator/observation records. Explain missing data in the Reporting manifest. Existing generic Finance actual amounts remain readable, with no receipt label or cash subtotal contribution.
4. **Prepare the manifest.** Choose agreement, period and explicit receipt/finance/outcome rows. Save the draft, then run Prepare sources, which validates the factual dependencies and returns a digest/preview without requiring this manifest to be approved. Save that digest through the ordinary revisioned manifest PATCH, which clears any old approval. A different authorized contributor reviews the shown source versions and approves the manifest through the existing approval command. The UI shows invalid sources as blockers without disclosing hidden records.
5. **Preview.** Show award context separately from period receipts/spending, budgets separately from actuals, observations individually, gaps, excluded/ineligible source explanations and field-to-source drill-down. Preview states the selected-source coverage, not that every transaction/measurement in the organization was found.
6. **Freeze deliberately.** A CSRF-protected command includes the exact preview ID/review hash and a random idempotency key. Recheck under the organization lock; any stale/unauthorized required source prevents the entire freeze. No partial report and no automatic fallback to an older snapshot.
7. **Read, export and revise.** Future source edits leave the report unchanged. Display its freeze date, checksum, period, method version, approval meaning and later correction links. A board reader cannot navigate from this projection into restricted source payloads, attachments or full financial records.

## Source eligibility and traceability

The server reads persisted current envelopes, not client-supplied approval flags or `visibleRecord`'s historical reader projection. Every included factual/narrative record must have:

- The exact organization/module/ID, current revision and content hash.
- Current server-created approval with `approval.status=approved` and `approval.revision === record.revision`, an approval actor different from `lastEditedBy`, and a server timestamp. Record the original approval provenance; do not claim a reviewer remains a current staff member or professionally qualified.
- A permitted report-source workflow state, current module read/export authority for the creator and the exact explicit program anchor. Administrators do not bypass source approval or period/currency rules.
- Valid typed data and the required dependency closure, with no missing, deleted, cross-tenant or out-of-scope dependency. Check reference _identity_ against current records even when its private contents are deliberately omitted from the projection.

Freeze these source categories: approved Reporting manifest; agreement; program; current approved application plus its historical submitted snapshot; selected gift-reference receipts; selected budgets/allocations/actual references; selected outcome observations and their indicator definitions; any parent budget needed to interpret an allocation. **Frozen v1 amendment limit:** block an agreement with a linked noncancelled `kind=amendment` record rather than guessing whether it is effective. The registry has no effective-date/precedence model. A later typed amendment design can replace this conservative limit; an unchecked “latest amendment wins” rule cannot. Restriction records are not silently merged: v1 uses the current approved agreement's explicit restriction code/permitted use, and any disagreement is a blocker for operator resolution before review.

**Bind the manifest review to source versions with one digest.** Save `assemblyMethod=grant-report-v1` on the manifest before Prepare. `POST grant-reports/prepare` validates all factual sources while allowing the Reporting manifest itself to be draft. It returns `sourceDigest=hash({methodVersion,manifestId,selection,agreement,period,sourceRefs})`. `selection` is the normalized full manifest data excluding only `sourceDigest`; `sourceRefs` is the canonical, stable-sorted required dependency closure with revisions, current approval facts and content hashes. Include stable manifest identity, but exclude the manifest envelope's revision/status/approval from this digest: the subsequent normal PATCH/approval increments its revision and would otherwise create a cycle. All other manifest-data changes invalidate it. The normal manifest approval binds the saved digest plus exact data. Preview/freeze separately require current manifest approval and recompute equality with the saved digest. The final `reviewHash` separately binds the current approved manifest revision/approval, sourceDigest, complete compiled proof and preview actor/current membership. A source edit, later reapproval or selection change requires Prepare → normal save → independent manifest approval again. Permissions are rechecked independently; an old digest never grants scope. A manually forged/imported digest has no effect without an exact server recomputation and a fresh valid manifest approval. No special approval hook, giant typed JSON field or new reviewer role is needed. Freeze preserves the complete closure for later inspection, not merely the digest.

Only records actually used by a calculation or displayed claim enter the source closure. A linked funder contact, file or document is not silently copied. Application/contact/document references may remain opaque IDs in staff provenance; no donor details, private agreement files or contact records enter the board projection.

Allow current approved applications in `submitted` or `decided`; preserve the separately labeled submitted snapshot's own revision/hash and submission reference. Do not relabel the historical snapshot as current or require its revision to equal the current envelope after a valid transition. Locate the server-created submitted artifact in the append-only `record.transitioned` history for this exact application ID/version/submission reference; a later approval can replace the working envelope's `snapshot`, so `record.snapshot` alone is not a reliable historical submission locator. Freeze that artifact's event identity, snapshot revision and content hash as historical provenance. Missing/mismatched provenance is a blocker, not invented application history. The current envelope's approval must still be valid. Only the narrowly authorized source artifact is inspected, not the organization's general audit feed. Establish exact allowed states for all other source modules in one tested server map before implementation; suggested states are approved/active/reporting/closed for agreements, approved/active/reconciled/closed for finance, approved/active/reconciled/acknowledged for gift references, approved/included for observations and approved/active/closed for programs. Every receipt also needs receivedDate/receiptReference even if its workflow state does not require them generically. Cancelled/superseded/review/draft sources are ineligible.

Each source entry contains `{moduleId,id,revision,status,dataHash,approval:{revision,actorId,at},snapshotRef?}`. Hash a canonical allowlisted envelope, excluding volatile reader decoration; reuse the existing canonical `hash` helper and pin `methodVersion=grant-report-v1`. Private approval reasons stay in record/audit access, not the board projection. Each derived field has a trace entry with exact source references and JSON field paths, operation version and missingness/exclusion decisions. File metadata may be referenced privately by checksum; no file bytes or fetches are needed to assemble this slice.

## Period, money and measurement rules

**Period:** strict Gregorian `YYYY-MM-DD`, inclusive start/end, start ≤ end. Require the report interval to fall within the agreement's explicit approved start/end. Do not infer fiscal year, local midnight, accrual period or pro-rate a straddling row. A gift receipt uses its explicit `receivedDate`; a classified spending row uses `actualDate`; a budget/observation uses its explicit start/end. Include period data only when fully contained. Reject a selected straddling/outside/missing-period row with an actionable issue; the operator must choose an appropriate period-specific approved row. Application and agreement are separately labeled lifetime/context sources rather than period transactions.

**Money:** retain `{minor,currency,precision}` exactly. The agreement establishes one explicit supported report currency/precision; every selected monetary input must match. An unknown amount may retain that currency and `minor:null`; do not synthesize a currency from the organization default. Reject mismatches rather than convert or silently drop them. Sum known minor integers with a BigInt accumulator; reject safe-integer overflow before JSON conversion. Keep award, planned commitment, period cash received, period externally referenced cash spent and recorded agreement spending in distinct rows. Never add award/commitment to receipts; never add agreement spending to selected actual spending.

For received cash and classified spent cash separately expose `knownSubtotalMinor`, `knownCount`, `unknownCount` and a clearly named partial/complete status **among selected references**. If any selected amount is null, the headline total is null; a secondary known subtotal remains available with its missing-count label. An empty selection displays “No receipt references selected,” not “No cash received.” A selected known zero remains zero. Budgets/scenarios/allocations are separate contextual rows; do not sum both a parent budget and its allocations into spending or a misleading grant budget total.

Reject duplicate financial source IDs, duplicate receipt `(externalSystem,receiptReference)` and duplicate classified spending `(externalSystem,externalId)` within a report. Require nonempty normalized external identity; use any additional externalId as a second duplicate check for receipts. This catches the same referenced line twice; it cannot establish that two different external IDs represent different cash movements. Require the manifest reviewer to acknowledge source selection/completeness. Refunds, netting, FX, split transactions, cross-grant apportionment, accrual calculations and tax/accounting certification are outside this slice. Existing nonnegative money validators remain in effect; do not introduce negative cash through a title or signed variance field.

**Measurements:** observation and linked indicator units must agree exactly; unlike units never share a total. Preserve value `null` separately from measured `0`, known/unknown denominators, geographic scope, period, evidence label, collection method, source URL and limitations. Rate/percentage values need a positive denominator under the existing validator. Do not back-calculate numerator counts or average percentages. “Independently reviewed” is a source-entered evidence label, not proof that the software's record approval establishes independent research. Harms can be included as individual observations with the same rules. Causal attribution is never derived.

## Minimal API and immutable format

All routes are same-origin, authenticated, no-store and use the current CSRF contract for POSTs. Errors retain `{ok:false,code,message,issues?}` with 401/403/404/409/422; no raw SQL, hidden-source titles, approval reasons or external secrets. No new provider, cron, send command or public route.

| Route                                       | Contract                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/orgs/:org/grant-reports/prepare` | `{reportingRecordId,revision}` → `{ok:true,sourceDigest,report,issues:[]}`. Read-only preparation accepts a draft manifest but requires all other included factual sources to be currently approved. It does not save the manifest, issue approval or freeze a report. The client deliberately applies the digest with normal revisioned PATCH, then obtains ordinary independent approval. |
| `POST /api/orgs/:org/grant-reports/preview` | `{reportingRecordId,revision}` → `{ok:true,previewId,reviewHash,expiresAt,report,issues:[]}`. The manifest supplies agreement/period/selection/audience. Structural/authority/source failures return a noncommittable 4xx with authorized field issues; no token that bypasses those failures.                                                                                              |
| `POST /api/orgs/:org/grant-reports/freeze`  | `{previewId,reviewHash,idempotencyKey}` → `{ok:true,report}`. Freeze recomputes all source/approval/scope/hash/period facts. Same successful actor/key/body returns the same saved report after current read authorization; a changed body/key binding conflicts.                                                                                                                           |
| `GET /api/orgs/:org/grant-reports?cursor=…` | `{ok:true,reports:[safe metadata],nextCursor}`; 20/page. Staff see eligible full grant reports; board readers see only board-audience reports wholly within their current program scope. No source payloads in list metadata.                                                                                                                                                               |
| `GET /api/orgs/:org/grant-reports/:id`      | `{ok:true,report}` chooses the stored staff or board representation by current server authority. A board reader cannot request a different projection using a query parameter. The board projection has its own checksum and a root/report identity binding.                                                                                                                                |

Keep generic `POST/GET /reports` and old payload readers unchanged for reports without a new `kind`. Add an explicit discriminator before treating a payload as the new format. The new UI can list both report types and select the matching reader. Do not make legacy `payload.modules.every(...)` assume a new payload lacking `modules`, and do not expose new grant reports through the legacy full-reader route to a board role. For minimal coexistence, retain `modules` with frozen staff source envelopes in a new grant payload; audit/list/reader branches still use the explicit kind.

Suggested stored payload outline:

```text
format: charitology-os-report
kind: grant-period
schemaVersion: 1
methodVersion: grant-report-v1
id, orgId, title, createdBy, createdAt
manifest: {id, revision, hash, sourceDigest, audience}
agreement: {id, revision, programId}
period: {startDate, endDate, convention: inclusive-dates}
currency: {code, precision}
sections: {grantContext, finances, observations, gaps}
trace: [{outputPath, operation, sources, missingness}]
sourceRevisions: [{moduleId, id, revision, dataHash, approval, snapshotRef?}]
modules: [frozen staff source envelopes]
boardProjection: {kind, id, period, approved allowlisted sections, trace, checksum}
supersedes: {id, checksum, reason} | null
authorization: {role, programIds, membershipRevision}
command: {actorId, keyHash, previewId, reviewHash}

```

Specify checksum input precisely: remove only the object's own checksum field; canonicalize keys/dates with the existing helper. A nested board checksum is computed first over its own projection. Never represent the board checksum as the hash of a private full payload. Hashes detect changes; they are not signatures by an accountant, independent reviewer or trusted timestamp authority. The private command/provenance fields do not appear in board JSON/print output.

## Minimal schema and bounds

- Reuse append-only `os_reports`; no mutable grant-report table. Add a partial unique index for grant report `(org_id, actor command key hash)` to enforce replay under concurrency. Preserve both trigger and runtime-role UPDATE/DELETE restrictions. A new edition links backward without updating the previous row.
- Add one short-lived `os_grant_report_previews` table with organization, preview ID, actor, approved manifest revision, reviewed payload/proof, review hash, expiry and creation time. FORCE RLS, composite tenant identity and constrained runtime grants. Delete committed previews after the report transaction; successful replay resolves through immutable report command identity. This avoids permanent import-archive slots. Recheck current actor authority before either new freeze or replay.
- Frozen bounds: 100 combined explicitly selected receipt/finance/outcome rows; dependency closure ≤250 records; canonical full report ≤2 MiB; four live previews and ≤8 MiB preview payload per organization; ten-minute expiry; preview/freeze request bodies ≤16 KiB; list pages20. Existing reference fields already cap each list100. Reject an over-bound report as a whole with no approval/report/source mutation. Count previews and final reports in the ordinary organization storage budget; never consume the emergency privacy-action reserve. Charge append-only audit and final report space atomically.
- Exact field additions: Fundraising `agreementId`; Finance `actualClass`, `actualDate`; Reporting `assemblyMethod`, `sourceDigest` (64 lower-case hex), `receiptIds`, `supersedesReportId` (opaque report reference) and `revisionReason`. Fields are nullable and backward-compatible at record parsing. The new assembler validates sources at Prepare and requires digest/current manifest approval at Preview/Freeze; the existing approval handler remains unchanged. Generic old drafts do not become invalid solely because they lack new fields. A correction reference must point to the same organization/agreement/program and preserve an inspectable earlier checksum.
- Export includes the new immutable report payloads under existing `reports`. Preview data is transient and excluded. Restore keeps source report JSON/checksums in the private original archive, resets imported record approval and **does not recreate active approved grant reports, approval identity or board grants**. The original archive remains administrator-only. An imported manifest must be reviewed and newly approved before any fresh report. New table grants/RLS and quotas require migration + isolated-role tests.

## UI and permission rules

Add “Grant report” beside the existing “Module snapshot” function. Start from an approved Reporting manifest; show agreement/program/period, selected source counts and blockers. Link to the ordinary editor/approval flow rather than approving silently in the wizard. The preview shows missingness before any prominent subtotal, offers source drill-down and requires an explicit “Freeze this reviewed version” action. No automatically checked evidence assertion or public-publish button.

Creators must currently have Reporting write/export permission and read/export permission for every copied source module plus current scope for every source in the closure. A program lead who lacks a required category sees an unavailable explanation, not a reduced report silently presented as complete. Require current export permission on each full staff download. A formerly authorized creator loses read access when membership/scope ends. Board readers require current Reporting read permission, `audience=board`, and matching explicit program scope; they receive the fixed approved projection only. External reviewers remain excluded in v1 until a report-specific audience grant exists. No new team role is created.

The board projection includes approved report title/period/program label, agreed restriction summary, separate financial facts, individual aggregate measurements, gaps and traceable safe source IDs/revisions/hashes. It excludes raw application narrative, donor/contact references and notes, personal identifiers, owner/editor/reviewer IDs, internal reasons/comments/history, external ledger/receipt IDs and links, unrestricted file metadata, attachment bytes and private authorization/command metadata. Approved summary/limitations are deliberately authored for that audience; a keyword filter cannot guarantee no personal data. Show that responsibility during manifest preparation and review. Do not auto-publish or send the report.

Use text nodes and safe HTTPS links only, no `innerHTML` from saved sources. Keep labels/keyboard focus, loading/error/empty states, responsive reading and print styles. A stale preview remains visible as historical preview with Freeze disabled and “Refresh preview” available; it never destroys unsaved manifest drafts or repaints private data after logout/revocation. Reuse the existing generation/revision guards. JSON filenames are sanitized; CSV is outside the first-slice output.

## Acceptance and verification before calling O2 implemented

Use a new isolated random Postgres schema with the constrained FORCE-RLS runtime role, real authentication/session APIs and at least two synthetic authorized contributors. Any server-seeded approval is explicitly fixture provenance. No production records, accounting systems, real funder submissions, paid services or provider sends are needed.

1. **Complete chain:** synthetic opportunity/application versions → second-account approval → submitted artifact → approved restricted agreement → explicitly agreement-linked gift receipt and dated planning/spending references → indicator/observation → approved source-pinned Reporting manifest → preview/freeze/read/JSON/print. Verify an explicit receipt is not the award and all output paths resolve to the frozen source revision/hash. Task/deadline access works separately without claiming task completion proves grant compliance.
2. **Arithmetic and missingness:** e.g. award USD1,000.00, explicit cash received USD300.00, spending USD100.00, unrelated budget USD800.00. Output never calls the award/budget cash received. Add a selected unknown receipt: headline receipt total becomes null, known subtotal stays USD300.00 with one missing reference. Empty sources, true zero, JPY/KWD precision, unlike currency, duplicate external line, max safe integers and overflow all have defined tested outcomes.
3. **Measurements/period:** exact0 vsnull; percentage denominator validation; mixed units and different indicators; overlapping populations not pooled; same-day bounds/leap dates; missing/straddling/outside periods; explicitly scoped harms/source limitations. No inferred causality or fabricated source coverage.
4. **Approval and TOCTOU:** self-approval rejected; Prepare accepts a draft manifest only with approved factual dependencies; forged/missing digest blocked; normal digest save clears approval; manifest approval/revision increments do not create a digest cycle. A later source edit/reapproval requires a new digest and manifest review. A stale approved reader snapshot does not pass; a changed source, approval, parent budget, manifest, membership scope or replacement-report identity between preview/freeze produces no report/audit partial write. Historical submitted snapshot/current decided application provenance remains accurately distinct.
5. **Permissions:** two organizations, multiple programs, unscoped source, revoked creator, contributor, scoped board reader and external reviewer. Verify private fields absent from board JSON/DOM/print, restricted files inaccessible and board read of one report does not reveal another. Exact report lookup and list obey the same rules.
6. **Immutability/replay:** SQL UPDATE/DELETE denied; later evidence edits leave old checksum/bytes unchanged; correction creates a second row with approved reason; concurrent same-key freeze creates one report; mismatched key/body/actor cannot replay another report. Legacy generic report list/detail/export and old checksums still work.
7. **Backup/restore/quota:** backup preserves original payload/checksums; restore keeps historical reports only in the source archive and imported manifests unapproved; no board grant/preview/approval reactivation. Test maximum selection/closure/body/report/preview limits and byte budget under concurrency. Failed quota leaves all prior data and report counts unchanged.

## Frozen integration details

- Source states are explicit: Programs `approved/active/paused/closed`; grant applications `submitted/decided`; agreements `approved/active/reporting/closed`; Finance `approved/active/reconciled/closed`; Fundraising gift references `approved/active/reconciled/acknowledged`; outcome indicators/observations/harms `approved/included`; Reporting manifests `approved/frozen/issued`. Every included current record still needs valid exact-revision independent approval. Prepare accepts an unapproved manifest only, with saved `assemblyMethod=grant-report-v1`. It does not require a manifest workflow transition or issue approval.
- Money currency/precision comes from the explicit agreement awarded-money object, whose amount may remain null. Missing source money stays null. Every selected known/unknown money object must match that currency; no organization-default currency or currency conversion is inferred. Receipt identities use normalized external-system names plus exact trimmed receipt references; spending identities use normalized external-system names plus exact trimmed external IDs. These controls do not prove that different identifiers are different cash movements.
- The source digest excludes manifest envelope revision/status/approval and its own data field. All other manifest data, stable ID, method and exact factual source closure are bound. Final review identity separately includes current manifest revision/approval, actor and membership revision. Saving a digest through the normal PATCH invalidates prior approval. Later source reapproval or manifest-data change requires a new digest/save/independent approval.
- Board checksum input includes its own immutable report ID, method, safe source references and allowlisted content, but excludes the private full-payload checksum. Compute board checksum first, then the full report checksum including that board result. No checksum cycle, private actor/command/source-envelope fallback or claim that a board digest verifies the private payload.
- Route service interface is `grantReportRoutes({c,org,user,member,tail,method,input,url,settings})`, called inside the existing tenant transaction and organization mutation lock. It returns a Response or null. Prepare, Preview and Freeze bodies are bounded at 16 KiB by the outer handler. New preview storage is tenant FORCE RLS and ordinary quota only. Existing module-snapshot routes retain their permissions and old shape; an explicit grant-report discriminator governs the new safe reader and prevents legacy full-reader access from bypassing the new authority check.
- Eight nullable typed fields are added: Fundraising `agreementId`; Finance `actualClass/actualDate`; Reporting `assemblyMethod/sourceDigest/receiptIds/supersedesReportId/revisionReason`. Historical drafts keep their previous meaning. All new report preparation is deliberately manual; no email, new paid service, provider connection, public publication or production fixture data is added.
- A frozen grant edition is unique for its organization, approved manifest ID/revision and source digest. After rechecking the current preview and source authority, another key for that exact edition returns the existing report instead of appending a duplicate. This handles a lost freeze response followed by a browser reload without making a new key permission to repeat an uncertain mutation. Exact original command replay remains body-bound and requires current report-read authority. Stale new previews still fail before this lookup; a correction requires changed manifest data, fresh source preparation and independent approval. The existing report and its original command identity remain immutable.
- New grant-report endpoints have separate durable per-account bounds of 120 reads/hour and 60 prepare/preview/freeze commands/hour, using hashed account keys. They do not use a provider send allowance. The existing whole-organization exit/export remains a separate route; no exact-time report availability or unbounded compilation promise is made.

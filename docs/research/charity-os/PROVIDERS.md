# Charity OS: existing systems and reuse research

Checked October 25, 2026, America/Los_Angeles. **Editorial draft; AI-assisted documentation review.** No platform was installed, purchased or independently security-tested. Provider statements describe available scope, not proven Charitology integrations. This is a bounded sample of ten systems, not a complete market census or a ranking.

The root agent attempted Stripe Directory using the current official CLI; the service rejected its user agent. This review therefore uses official documentation, source repositories and public GitHub metadata. `providers.json` contains the structured dossiers and 60 source records. `github-observations.json` retains exact commit URLs, UTC dates, archive flags and observed license detection. A recent push does not establish release support or production safety.

## What this means for the OS plan

**Plan Charitology as an open operations and learning layer with optional connectors.** Keep organization context, projects, grant obligations, tasks, observations, evidence and reporting close together. Link to established fundraising, financial, membership and field systems where they already meet the need. This is a design inference from the documented landscape, not evidence that every charity wants the same product.

The first shared pilot should help a small team answer: What did we promise? What is due? Who owns it? What happened? What evidence supports that conclusion? What should change? Its depth labels should describe relief, repair, prevention, structure or source; they must never become a score for a charity or a worker.

Do not define “complete OS” as rebuilding every category. A membership association, mutual aid group, grantmaker and frontline service organization have different records, access needs and obligations. The product should let teams enable appropriate modules and keep control of their data. Interview/pilot evidence must decide the order.

## Maintenance and compatibility findings

- **ERPNext core and nonprofit addon are different maintenance decisions.** [`frappe/non_profit`](https://github.com/frappe/non_profit) was archived July 31, 2025. The observed default-branch commit is June 12, 2024, and its README refers to v14 documentation. The [marketing page](https://frappe.io/erpnext/for-non-profits) still describes nonprofit workflows. Treat the archive as a dependency gap; do not silently promise current-version compatibility.
- **OCA’s repository name is not a shipped suite.** The observed [`vertical-ngo` 19.0](https://github.com/OCA/vertical-ngo/tree/19.0) and [18.0](https://github.com/OCA/vertical-ngo/tree/18.0) trees contained scaffolding, without addon directories. [`vertical-association` 19.0](https://github.com/OCA/vertical-association/tree/19.0) contains seven listed membership-related addons; [18.0](https://github.com/OCA/vertical-association/tree/18.0) has a different set. Migration coverage must be checked per module and branch.
- **Tendenci has a deliberately bounded API.** Its [official API guide](https://tendenci.readthedocs.io/en/latest/topic-guides/api.html) documents read-only access to entities, events, memberships, users and groups. Do not estimate two-way synchronization as a small configuration task.
- **OSCaR’s recent repository activity does not modernize the runtime.** The [recorded `.ruby-version`](https://github.com/Children-in-Families/oscar-web/blob/9dd3a12e18eecc8a5848c44cbb332a6887969ff0/.ruby-version) says 2.3.7 and the [recorded Gemfile](https://github.com/Children-in-Families/oscar-web/blob/9dd3a12e18eecc8a5848c44cbb332a6887969ff0/Gemfile) pins Rails 4.2.5. No production deployment is recommended from this inspection.
- **CaseLight’s maintainer distinguishes a working pilot from production approval.** Its [SECURITY.md](https://github.com/Lighthouse-Nonprofit/caselight/blob/f30578c3b828f45fba5d33cdb8097457edfda901/SECURITY.md) requires synthetic/representative evaluation data and identifies further organizational and infrastructure decisions before real records. The compliance folder is documentation, not independent certification. It does not replace named operators, incident owners and retention decisions.
- **CiviCRM publishes security fixes that integrations must track.** Its [advisory page](https://civicrm.org/advisory) records APIv4 authorization issues and fixes in August 2026. This supports keeping exact supported versions, update ownership and authorization regression tests in a connector plan. It does not establish that a current deployment is vulnerable.

The JSON includes exact default-branch commits rather than star counts or a single “active” score. Branches may be development branches. Closed products have no public-repository maintenance assertion in the matrix.

## Cost and license distinctions

Open-source code does not eliminate hosting, migration, support, backups, patches, training or operator time. A cost estimate must separate these from license fees. Before adopting or copying code, check the exact distribution and every dependency; confirm reuse obligations before adoption.

- [CiviCRM](https://github.com/civicrm/civicrm-core), [Kobo KPI](https://github.com/kobotoolbox/kpi) and [CaseLight](https://github.com/Lighthouse-Nonprofit/caselight) expose AGPL-3.0 repository licensing. [ERPNext](https://github.com/frappe/erpnext) and [OpenProject](https://github.com/opf/openproject) expose GPL-3.0. Tendenci’s [README](https://github.com/tendenci/tendenci/blob/main/README.md) and [license](https://github.com/tendenci/tendenci/blob/main/LICENSE) specify GPLv3 or later even though automatic GitHub detection returned `NOASSERTION`.
- [Odoo Community is LGPLv3; Enterprise has separate terms](https://www.odoo.com/documentation/18.0/legal/licenses.html). OCA repositories warn that individual addon manifests can carry different licenses. Preserve upstream licenses and attribution; do not relabel copied code as MIT.
- OpenProject’s [current pricing page](https://www.openproject.org/pricing/) showed free Community with no minimum users and a EUR5.95/user/month Basic card with a 25-user floor. Hosting choice, term and locale affect the actual quote.
- Givebutter’s [pricing page](https://givebutter.com/pricing) differentiates donor tips, platform fees, processor fees and paid contact-tier features. Its [mobile documentation](https://help.givebutter.com/en/articles/6868930-how-to-use-the-givebutter-mobile-app) has a channel-specific fee treatment. The OS should show actual net/fee records instead of assuming all donation channels share one fee model.
- The canonical [Salesforce U.S. page](https://www.salesforce.com/nonprofit/pricing/) opened for this review lists Core at USD70/user/month and Advanced at USD125, billed annually; it states eligible nonprofits may receive ten Core licenses at no cost. Older indexed regional/query variants showed USD60/100. Use the current written offer for procurement, and separate eligibility, grantmaking, portals and implementation from the base license.
- Kobo’s [account documentation](https://support.kobotoolbox.org/creating_account.html) confirms a Community plan and its [usage documentation](https://support.kobotoolbox.org/account_usage_limits.html) identifies quota categories. The pricing fetch returned 403. Numeric quotas and current paid prices are intentionally unverified here.

## Suggested reuse boundary and connector acceptance tests

These are proposed requirements, not assertions about existing Charitology capabilities.

| Boundary | First proof before building more |
| --- | --- |
| CRM and communications | Import a small synthetic contact set; preserve stable IDs, duplicates, consent scope and suppression. A donation must not imply newsletter consent. Use least-privilege credentials. |
| Grants and project delivery | Map funder promise → reporting obligation → owner → deadline → project → observation. Show amendments and versions. A planned award, approved award and money received are separate states. |
| Financial records | Keep an external accounting source of truth. Link transaction/restriction references; reconcile amounts and currencies. Do not call a planning ledger audited accounts. |
| Field evidence | Use authorized aggregate/anonymized data first. Preserve form version, indicator definition, numerator/denominator, period, missing values and collection method. Never equate an observation with a causal finding. |
| Two-way integrations | Demonstrate authenticated webhook validation, duplicate/replayed events, out-of-order updates, deletion, retries, rate limits, reconciliation and connector disconnection. Separate test from production. |
| Portability and exit | Export records, relationships, field definitions, history and allowed files. Restore into a clean test organization; compare totals and links. A download button alone does not prove exit. |
| Access and tenancy | Test two unrelated organizations and multiple roles across UI, API, exports, attachments, search and background jobs. Project groups or filters alone are not a tenant boundary. |
| Sensitive casework | Defer until a specific operator owns consent, retention, security, safeguarding and incident response. Evaluate specialized tools with synthetic cases first. |

For discovery, show the existing local OS and test these tasks with willing pilot organizations. Record failures, completion time, assistance needed and missing fields. Ask which current system is authoritative, what they cannot export, who maintains it, how volunteers hand work over, and what happens when internet access or funding stops. Separate demonstrated needs from attractive feature ideas.

The research supports a modular plan and explicit evaluation spikes. It does not yet justify selecting one backend, promising universal coverage, migrating real records or replacing every provider.

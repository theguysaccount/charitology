## Separate states, without inferred transitions

Four separate fields render four separate labels:

1. Incident lifecycle: `ongoing | recovery | ended | unknown`. Known values require status refs to note items whose target is exactly that incident, whose basis is `source-self-report`, and whose typed `status` observation has that same target kind and exact value. An operation/appeal note or a recovery observation is rejected as support for incident-wide ended. Source-specific adapters admit the observation only from an explicit statement with a locator; the note's authored prose alone cannot grant a status. An incident's end is uncollected in the initial slice unless an incident-wide end is explicitly supported; no elapsed date establishes it.
2. Response-operation status: `ongoing | ended | unknown`, scoped to an issuer, code and original URL. Its period is only that operation's period. Appeal status: `open | closed | unknown`, scoped to its own issuer/code/terms. `recovery` is not a substitute appeal/operation state. An appeal deadline alone does not close it. Status claims with incident targets use only incident lifecycle states. Every known status claim requires a status-role source ref whose note has the identical target and typed status value. A note has exactly one scoped status or null; status-role requires a nonnull observation, and non-status notes carry null.
3. Editorial placement: `follow-up | archive`, dated with a reason. Unknown or ongoing incidents may be archived because this collection is no longer following them. Resumption appends another incident version. Nothing is silently reopened.
4. Review freshness: canonical `checkedAt`, `recheckAfter`, and edition `asOf`. At exactly `recheckAfter`, review is overdue. Static pages, JSON, CSV and API compute this solely against edition `asOf`. They never consult a build/device clock or infer current source validity. Display: “As of this capture,” with explicit dates and an always-visible not-live/coverage warning.

The optional browser warning accepts only a supplied canonical UTC-millisecond device instant for a qualified extra display; it never normalizes a caller's offset/locale string. Invalid/before-capture clocks are unassessable. A later clock may show that review appears overdue, but never “verified current.” It cannot change pins, editions, data, archive placement or exported bytes. No script is needed to read sources, limits or deadlines.

`standing` (`reported | disputed | withdrawn | corrected`) describes a claim's editorial treatment, separately from its publisher-reported status. Disputed statements remain attributed separately; no average or winner is calculated. Withdrawal/correction appends a version and a reason. Missing/failed access produces an access record and coverage loss, never zero needs. Quantities are literal strings or null: `reportedText: "0"` remains distinct from null. First real sources need no financial or beneficiary quantities.

An unavailable source version has null original/published/sourceUpdated/documentCreated/documentModified/dateDiscrepancy, no literalFields, and an authored access-only note with null statuses. It records this attempt, rather than copying a previous body's dates/facts under a new missing-body pin. Previous retrieved versions remain independently available through their original exact pins. Access-only refs cannot support incident/claim factual statements.

## Exact encoding, dates and closed bounds

All public DTO fields/unions are exactly those in the paired interfaces. Unknown keys, duplicate decoded keys, accessor/proxy inputs, decorated/sparse arrays, symbols, unsafe prototype keys, nonfinite numbers, malformed UTF-8/surrogates, BOM, unsafe paths and unrecognized enum/descriptor/method values fail complete admission. No trimming, default filling, sort of nested ordered arrays or source string/date normalization is permitted. IDs match `[a-z][a-z0-9-]{0,63}`. Record versions are positive integers, contiguous per identity; first `previous` is null and later pins identify the exact preceding version.

Canonical encoding `DI-C14N-1`: recursively sort object keys by JavaScript UTF-16 code-unit order, preserve every array order and exact string, use JSON string/finite integer encoding, UTF-8, no BOM. Stored JSON files end in one LF. Hash a record's object excluding only its `hash` using SHA-256 over `charitology-disaster/v1/` + kind + LF + canonical object + LF. Registry uses kind `registry`. A file pin instead hashes its complete stored bytes. No hash cycle is allowed.

Reported day is a valid Gregorian day, years1000–9999; it stays a day. Reported instants retain the exact source/parser-observed literal and reported offset beside canonical UTC milliseconds. Offset is `Z` or `±HH:MM`, at most14:00. The adapter's declared mapping must support that conversion. DMY and English month/day mappings are explicit descriptor rules, never locale guesses. Unknown or unsupported month-only/day-without-year precision remains null, with its original phrase in the note. `sourceUpdated`, `published`, document metadata, retrieval, incident/operation period and editorial checks are separate fields. No chronology is inferred from those different roles. A period with two known endpoints requires the same precision: compare day/day lexically and instant/instant canonically; reject mixed day/instant endpoints rather than invent a midnight. A candidate may retain the unsupported endpoint's literal with a null endpoint and a limitation. Known endpoints must not end before start. Recheck must be strictly after check; editorial checks cannot be after edition `asOf`.

`Source.original.mediaType` identifies the detected supported content kind. Its separate `responseContentType` preserves the exact observed HTTP Content-Type field (or null), at most256 UTF-16 units; never overwrite application/octet-stream with application/pdf. The initial IFRC body is detected PDF with its original response MIME retained. Repeated/ambiguous Content-Type fields or malformed headers fail preparation; no silent concatenation is claimed. PreparedOriginal carries the same original metadata unchanged.

Require edition `asOf <= capturedAt`; every included Source.retrievedAt and Incident.checkedAt/editorial.decidedAt must be `<= asOf`. Both capture instants are sealed maintainer preparation observations, not a claim that a source was current or a trusted universal clock. The offline build validates those internal relations without obtaining its own clock. Attributed published/document metadata dates may disagree or follow retrieval; preserve their source literal and an explicit discrepancy instead of rewriting them.

## Paths, closure and outputs

Only these public core paths are admitted: `registry.json`; `methods/{id}/v{n}.json`; `records/{source|incident|claim}/{id}/v{n}.json`; `notes/{sourceId}/v{n}.json`; `editions/{id}.json`; `artifacts/{editionId}.json`. All are under `src/data/disaster-incidents/`. Reject unknown files, case aliases, encoded traversal, symlinks and orphan inventory. Edition identity is unique, version1, with sequence determined by its registry position; its `previous` is the exact prior edition pin. Other identities use contiguous versions. One note names its source identity/version and original raw hash, avoiding a source/note hash cycle. Source pins hash that note's exact bytes.

Every source/claim/incident/method pin resolves exactly; source-note ref item IDs exist and their roles/targets agree. Claim `incidentId` equals its target's incident. Status target/state compatibility is enforced above. Claim corrections/standing-related pins must resolve to a claim with the same `incidentId`; cross-incident links are rejected in this bounded version. Their declared order is preserved without interpreting order as priority. An edition includes exactly its incident pins, selected claim pins, and all required source pins for incident/claim refs plus its explicit access checks. No extra unrelated source is silently included. All retained versions must be reachable from at least one retained edition or a preceding-version chain; every retained edition remains in the registry. All previous source bytes/notes/versions stay immutable when a URL changes. Source availability does not retarget old refs.

An edition is sealed before exports. Its artifact manifest pins the edition and exactly `exports/{editionId}/edition.json`, `exports/{editionId}/edition.csv`, `exports/{editionId}/coverage.json`, in that order, each with complete bytes/hash. Those FilePin paths are relative to the same inventory root as `registry.json`; never basename-only or OS-dependent paths. These derived paths are the only additions to the core path allowlist above. The registry pins that manifest, avoiding edition/export hash cycles. Artifact manifests have no self-hash. Complete history exports include all core records/notes/editions/methods/manifests and exact registry, but not private originals or duplicated derived artifact bodies; they disclose that deterministic outputs can be rebuilt.

Complete-edition packets contain the full factual closure of one edition. Selected-incident packets preserve the exact original edition header and its inventory, include only the chosen incident/its claims/required sources/notes/method, and explicitly list boundary pins for omitted edition members and historical predecessors. Every typed pin is traversed, including Edition.changes.before/after; a noninternal change reference is an `editorial-change-reference` boundary. Reason precedence for the same pin is historical-predecessor, then unselected-edition-member, then editorial-change-reference. Every required factual ref, including claim corrections/standing links and supporting source refs, is internal; boundary pins are provenance links, never substitute evidence. No unclassified external pin is admitted. These packets are labeled incomplete history, excluded from history restore/import, and disclose source-note context broader than the selected claim. Complete history resolves every pin and has no such boundary. No new browser import feature is proposed.

CSV is a normalized deterministic record table: header `row_kind,id,version,path,sha256,json_value`. Include one row per packet header/method/incident/claim/source/note/boundary/limitation, in that declared kind order and the original DTO array order within kind. The header row has empty identity/path/hash slots; all six cells on every data row are encoded as `j:` plus JSON string encoding of the exact string cell (including the JSON-value cell). Then RFC4180 quoting, CRLF and final CRLF apply. This neutralizes `= + - @` and leading whitespace without guessing which strings are dangerous. Decoding removes exactly `j:` then parses one JSON string; an unencoded cell is refused. Original JSON is unchanged. A decoded `json_value` is the canonical complete typed value; nested arrays retain order. CSV explicitly includes null as JSON `null`, never blank/zero. JSON/API/coverage/HTML all use the same admitted packet and fixed `asOf`; no export clock is inserted.

Opaque `AdmittedHistory` is created only by complete history admission. Structural Packet outputs are detached data; each JSON/CSV serializer must independently admit and detach its complete current input, verify exact hashes/closed fields/factual refs/typed boundaries/scopes/limits and reject mutations or accessors rather than relying on TypeScript or a previous call. Serialization never grants historical Git/source authenticity or changes selection. `freshness` and `deviceWarning` validate their bounded display inputs but establish no history/edition authority; they cannot activate an edition or feed device time into canonical output.

Routes remain `/disasters/`, `/disasters/incidents/{id}/`, `/disasters/editions/{id}/`, `/disasters/editions/{id}/incidents/{incidentId}/`, `/disasters/sources/{id}/{version}/`, and edition artifact children. Static API names are exactly `disaster-incidents` and `disaster-incident-coverage`; wrapper `generated` equals edition `capturedAt`, not a build clock. Stable default incident ordering is ID order; declared source/ref/claim and history arrays are retained. Filters and sharing include the exact edition ID; no filter silently follows a later selected edition.

For each commit with data, admit its exact committed inventory and preserve the union of all earlier immutable files byte-for-byte. All retained bindings must remain statically available; unsupported older interpretation makes admission/build/install fail closed. Before accepting a new A/B, reproduce every retained edition's three outputs with its own pinned binding and compare every existing manifest's complete bytes/hashes. Keeping old output files without this reproduction cannot establish compatibility. The new edition alone uses the new method; older headers/arrays/bytes are never reinterpreted with changed semantics. The prototype's four fake methods are capacity examples of unchanged v1 recaptures, not evidence that production runtimes or Git objects exist.

Preparation is an explicit maintainer CLI, never a public fetch endpoint. Its candidate ID resolves only beneath the excluded prepared root; it cannot read caller-chosen arbitrary files. Descriptor IDs select exact allowlisted original URLs. At most one request is active, a30s request/body deadline, maximum2 reviewed same-descriptor redirects, original8MiB and original-body inventory32MiB. Relative candidate layout is exactly `request.json`, `proposal.json`, `originals/{candidate-owned-id}`, and `proposed/{public-inventory-path}`. The prototype writes an illustrative representation rather than exercising this real installer layout. `PreparedCapture.totals.preparedBytes` includes both JSON metadata files and all those body bytes, not only originals; core/derived totals separately account for all public proposed bytes. `proposalHash` hashes the prepared object excluding only itself with kind `prepared`. Its fixed64-character hash slot means complete byte-size accounting can settle before sealing; refuse unstable/oversized accounting. Abort/detach before a new selection; a failed request retains prior private bytes and becomes an access observation, not a replacement empty original. Hash complete raw bytes before preparing an authored note. Preparation cannot write the active tree. A detached proposal seals A, predecessor registry hash/presence, every proposed byte/path/hash, source-note locators, rights, target-scoped status, explicit changes, totals and warnings. Review is over that exact proposal hash. A clock/retrieval change creates another proposal, never retargets approval.

Installation uses one exclusive maintainer lock and an owned transaction journal/stage beneath the actual Git directory, on the same filesystem. After locking, reread A, required history, direct working bytes and exact predecessor registry. Stage/verify all candidate bytes; refuse any unsafe/orphan path or joint bound. Add new immutable files exclusively (never overwrite). Each addition records its exact FilePin and ordinary-file identity `{device,inode,ctimeNs}` from bigint filesystem stats, encoded as unsigned decimal strings of1–30 digits. Keep its open descriptor through the active attempt; before cleanup compare descriptor and no-follow path stats, identity, single-link ordinary-file status and complete bytes. Persist that identity after the final write. Unsupported/uncertain identity or any mismatch blocks automatic cleanup; even a foreign same-byte replacement is not owned. This is a cooperating-maintainer filesystem protocol, not protection against a privileged hostile process changing filesystem evidence.

Immediately before activation, recheck all captured authority and predecessor bytes. Persist `committing-head`, then atomically replace `registry.json` last. **That successful atomic replacement is the commit point**, even if the process crashes before journal/readback. Flush files/directories where supported; unsupported durability is reported, never silently called crash-durable. Return installed only after exact active-head and full inventory readback. Normal failure/cancel before the commit point cleans only additions still proven owned; old files/head remain. A crash, uncertain rename result or cleanup failure blocks build/install as recovery-required until reconciliation under the same lock.

Recovery compares actual registry bytes to the journal's exact `predecessorRegistryFile` (or absence) and `desiredRegistry`. If predecessor matches, the transaction is uncommitted: clean only exact owned additions or resume the same proposal after full admission. If desired head matches and its complete inventory admits, the transaction committed: retain its files, mark head-committed and return already-installed, even if the journal still says committing-head. A third, malformed, absent-when-not-expected or unreadable head is uncertain: no automatic rename/delete/rollback; retain the journal and require explicit maintainer resolution. A desired head with broken inventory is also recovery-required. No false promise of complete rollback under arbitrary filesystem failure is made.

Cancel before the commit point revokes further work and cleans owned additions. If cancellation races atomic replacement, finish only bounded reconciliation/readback: return canceled only if the predecessor remains and cleanup completes, already-installed if desired head/full inventory verifies, otherwise recovery-required. It never rolls back an activated edition. Exact Retry uses the same proposal bytes/IDs/dates. If head already equals desired and inventory verifies, return already-installed. If predecessor/A/input differs, return stale without cleanup of foreign files; no automatic rebase or duplicate edition. A crash journal may only resume that exact transaction or reconcile/clean its proven owned additions. First source seed installation requires actual A plus separately reviewed B; fictional commits/`.invalid` sources below cannot satisfy the production Git/source allowlist gate.

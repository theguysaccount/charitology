# Local program relationships

Pre-implementation proposal · October 27, 2026 · AI-assisted · review: draft. No graph software, migration, browser acceptance or shared operating authority is established by this document. Read the [exact interfaces](PROGRAM_GRAPH_INTERFACES.md) before implementation.

## Bounded recommendation

Add one private browser-origin register for relationships among deliberately captured records from the nine partner-program workspaces. The useful journey is **capture selected saved records → connect a proposal, project, evidence note or follow-up → inspect the connected work → refresh from another complete source copy → resolve changed or missing endpoints → export and restore the graph**.

Use the new key and Web Lock `charitology.program-graph.v1`. Leave all nine `charitology.partner-workspace-v1.<program>` keys and their version-1 backups unchanged. Do not insert relation fields into the old forms or maintain a hidden second copy of links there. The graph contains selected snapshots, not enforced foreign keys into live workspaces. It cannot change a source record, authorize a grant, approve a claim, reserve a place, execute a payment or establish a shared team.

This addresses the remaining local relationship part of W1. The already implemented [local-to-shared Charity OS migration](MEGA_LIST_ACCEPTANCE.md) is a different flow. Research registers, donor tools and shared OS records remain outside this first adapter set. They can later gain explicit, separately specified bridges; no automatic key discovery or identity merging is included here.

## Source identity and the migration choice

An enrollment creates a graph `SourceInstance` with a generated ID, exact program/adapter identity and a user-chosen project alias. Every import requires **new separate source instance** or **refresh this named instance**. Never infer the choice from a file name, program, title, shared record IDs or matching contents. When a new source overlaps an existing instance's IDs, show the overlap and require an explicit separate-copy acknowledgement. This makes two cloned Fund files distinguishable without pretending to discover their real-world lineage.

The source record identity inside an instance is `(sourceInstanceId, collectionKey, sourceRecordId)`. The graph gives that identity an opaque node ID. Renaming a title preserves it; changing an ID creates a different node. A refresh cannot relocate a node to a different collection or source. The same source ID appearing in another collection is rejected for that instance instead of silently retargeting old links.

The bridge accepts either a deliberately chosen complete partner JSON file or an explicit **Capture this saved workspace** action on a partner page. The latter reads only that page's known final key after the click. No scan, automatic synchronization or source-key write occurs. An absent or unreadable key is not synthesized as an empty source; offer raw recovery where readable, a chosen valid file or explicit source retirement. An intentionally saved empty workspace is a valid different case. The UI says that unsaved source forms are excluded; a failed-write source candidate should first be exported from its own page and chosen as a file. A final reread can reject a known source change during preview, but old writers do not share the new graph lock: the captured bytes are a dated copy, never a guarantee of the latest live state.

Validate the entire chosen source and retain its complete collection/ID inventory plus context, source byte hash and canonical value hash. The preview exposes the exact raw context map, including changed scope and authority statements, and its review hash binds that context. Copy full values only for selected new records and previously tracked records. Every refresh re-examines **all already tracked nodes of that instance**; there is no partial refresh. An empty selection can still refresh tracked nodes. Require an explicit acknowledgement that this is the complete chosen copy of the named instance. A valid but manually shortened file is still only that chosen copy: the UI says **not present in this capture**, never “deleted everywhere.” No absence is inferred from another program, an unselected source, a source read error or an unsupported file.

Older version-1 source files are imported explicitly into this **new graph format**, not rewritten in place. Exact strings and record IDs survive. Check byte limits first; fatal UTF-8 decoding, decoded duplicate-object-key refusal and a maximum JSON container nesting depth of 32 precede recursive parsing and canonical traversal. Apply the same admission rules to graph backups. Unknown future source fields, wrong versions, missing fields and invalid source records fail before graph assignment, with a downloadable copy of the chosen readable bytes. A future source schema needs a new frozen adapter version and explicit migration preview. Retain old adapters and snapshots; never reinterpret them against an edited current schema.

The graph backup does not embed the entire original partner file. It retains every selected snapshot, full source context, complete ID inventory (including unselected record identifiers) and provenance hash; unselected record values remain in the user's original source backup. Show this boundary before import and in exports. An 8 MB source file may fit the parser but its selected graph history may exceed the smaller graph backup bound. Reject that whole candidate with advice to select fewer records; never truncate or discard older versions.

## Relationships and useful views

All links are self-recorded planning relationships. There are six typed kinds: `related-to`, `depends-on`, `planned-work-for`, `evidence-note-for`, `decision-note-for` and `conflict-note-for`. The exact source-role allowlist is in the interfaces. No kind means that the source is true, evidence is causal or a decision is independently authorized. `depends-on` is the operator's declared planning dependency; it is not a causal effect.

| Existing work                | Initial manual relationship flow                                                                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Fund                         | Allocation `decision-note-for` proposal; ledger planning entry `planned-work-for` allocation; conflict note `conflict-note-for` proposal/allocation. Amounts retain their original strings and planning labels; stages are never summed together.                  |
| Incubator                    | Project `depends-on` gap question; experiment/milestone `planned-work-for` project; milestone may `depends-on` an experiment. A text finding is not a newly measured outcome.                                                                                      |
| Question Bounties            | Claim `evidence-note-for` specification; pledge `related-to` specification; decision `decision-note-for` claim. No accepted claim, contract or payout is inferred.                                                                                                 |
| Prize and Fellowship         | Nomination `related-to` criterion; conflict `conflict-note-for` nomination; deliberation/review `decision-note-for` nomination/project; milestone `planned-work-for` project. No automated winner or applicant decision.                                           |
| Donor and Nonprofit Advisory | Evidence note `evidence-note-for` scenario/action; action `planned-work-for` diagnostic; follow-up/learning `decision-note-for` scenario/action. Preserve source limitations and reasons; do not generate professional advice or observations.                     |
| Field Verification           | Finding `evidence-note-for` check; response `decision-note-for` finding; action `planned-work-for` check/response. Source text that says nothing was checked stays visible.                                                                                        |
| Summit                       | Role/production/follow-up `planned-work-for` session. Tentative calendar and session states remain tentative. No registration or announcement is created.                                                                                                          |
| Across programs              | Fund proposal `related-to` Incubator project; Nonprofit Advisory evidence note `evidence-note-for` Incubator experiment; Field Verification finding `evidence-note-for` Donor Advisory scenario. Each uses two explicit source identities and exact copied fields. |

Offer searchable source/collection lists, incoming/outgoing links, a bounded connected-work view, and filters for current, stale, unresolved and retired links. Selecting a node opens its captured fields, context, source details and immutable history. A source-page link uses a fixed known program route; it does not promise that the old page can open the captured ID or historical version. Legacy reference text remains visible beside the chosen link. No title matching, reference-code parsing, email identity matching or automatic inferred link is allowed.

`related-to` is symmetric with canonical endpoint order. Other links are directional. No self-links or duplicate nonretired kind/endpoints. Declared dependencies must remain acyclic, counting all nonretired dependency links, including unresolved ones; retiring a dependency explicitly breaks a cycle. Other relation kinds may form cycles. Link amendments change reasons/reviewed endpoint versions, not identity/kind/endpoints. Retire and create a new link to change those.

## Refresh, missing records and recovery

Every changed source record appends an immutable node version; a removed record appends a missing version without erasing its last values. A changed source context also appends versions for its tracked nodes: altered donor constraints, scope or authority text cannot leave a link apparently reviewed against the old context. Unchanged values and context reuse their prior node version. A title rename therefore changes the displayed current title while retaining the old title and the same node ID. A record absent from the complete chosen inventory becomes unresolved. Removing it from one source never deletes dependent work.

Links bind the exact endpoint versions the operator reviewed. States are derived, not editable claims:

- **Current:** both endpoints present in their latest accepted capture, neither source retired, and the link binds both current node versions.
- **Stale:** endpoints present but a bound version changed. A changed title, amount, evidence note or reference is visible; the old reasoning remains. Explicit link review is required before it becomes current again.
- **Unresolved:** an endpoint is missing in that instance's latest complete capture or its source is retired. Retain the old snapshot and show the exact affected links.
- **Retired:** the operator deliberately retired the relationship with a reason; retain its history.

A previously missing ID that reappears is a new node version with a visible identity warning. The old format cannot tell whether this is a genuine restoration or reuse of an ID for different work. Existing links remain stale. Reviewing such a link requires a deliberate same-identity acknowledgement for that endpoint if a missing/reappearance boundary occurred after its last reviewed version; later title edits cannot erase that warning. A new link to a node with such history also asks for the acknowledgement. Otherwise keep it unresolved/stale or capture the separate work as a new source instance. Never silently rebind by title or declare that a restored ID is proof of real identity.

Retiring a source retains snapshots and marks all its nonretired links unresolved. Resuming it requires a fresh complete capture. There is no destructive node/source/history deletion command in the first slice. Whole-register clear is an explicit previewed replacement with undo and a recovery download; history/count limits remain visible. A complete graph backup reconstructs the graph, including retired and missing versions. Restoring it never writes any original source key, establishes current live synchronization or creates shared permission.

## Storage, export and limits

Use the R2/R3 exact saved-byte and current-memory pattern in a new standalone adapter. Writes require Web Locks and hashing; unsupported capabilities are read-only. No initial write. Validate graph structure, immutable chains, known adapter hashes, derived classifications and exact complete-backup size before memory assignment. Check expected memory hash separately from observed saved bytes. A failed persistence attempt keeps a valid candidate exportable, labels it unsaved and retries that exact candidate without replaying the command.

An unseen foreign write before ordinary restore/clear preview must first block the page. A subsequent explicit recovery preview can adopt the newly observed bytes with a visible warning; commit still compares them exactly under the lock. Corrupt bytes are copied raw when readable; read denial is unavailable, not an invented blank. Undo, reload, restore and clear guard queued operations/generations and never erase a newer page's work. Keep the current form and its exact endpoint/source bindings recoverable; changed bindings require review rather than silently attaching to new versions.

The six raw form kinds are capture, new link, link review, source retirement, link retirement and source rename. Their exact field/binding name allowlists and comparison strings are fixed in the interfaces. Partial or malformed raw strings may be saved for repair, but unknown names fail and raw strings never grant command authority. A successful changing command may clear only a fully matching form, including every target, binding and field. Failed/no-op commands and unrelated, malformed, stale or newer forms remain intact. Source renaming has the same dirty warning and plain raw recovery path as the other forms; a stale capture draft must reacquire bytes and a fresh preview.

Proposed bounds: 20 source instances,100 captures total,500 graph nodes, 2,000 retained node versions, 500 links, 2,000 retained link versions, and a2 MiB complete pretty UTF-8 backup including its wrapper/newline. All history and retired rows count. Source files remain capped at8,000,000 bytes/500 records, with exact current source field limits. Raw graph draft: 40 string fields,16,384 characters per field,512 KiB total. A form that cannot fit beside the whole graph stays in memory with an exact plain raw-form recovery download; it is not mislabeled a valid graph backup. No background autosave can discard it.

Complete JSON includes the full graph, all captured selected values, unselected graph nodes, historical versions and saved raw draft. State this before download. A filtered CSV/Markdown packet includes only explicitly selected nodes/links plus the historical endpoint versions necessary to explain those links; list omissions and selection hash. Escape spreadsheet formulas. It is not a complete restore backup. Never fetch evidence URLs, upload files, export hidden credentials, transmit graph data to an API or seed real-person records. Browser-origin storage remains accessible to the site's own scripts and people using that browser; it is not encrypted confidential case storage.

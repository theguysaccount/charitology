# Charitology mail service

Private Node 24 Vercel Functions backend for the static Charitology site, using real Neon Postgres and the authorized existing Resend account through server-side Vercel Connect. No provider credential belongs in Astro, browser JavaScript or the repository. The service is deployed at https://mail.charitology.org. The existing delivery record documents sender verification and controlled inbox delivery; defaults in a fresh installation send nothing. The October 27 R5 release below adds fixed issues without creating or sending a new one.

## Install and verify

```sh
cd services/newsletter
npm ci
npm test
# Uses private .env.local; creates and drops an isolated temporary schema.
npm run test:db
npm run migrate
```

The database test uses only synthetic `example.invalid` addresses. It exercises actual PostgreSQL locking, simultaneous single-use confirmation, expiry/replacement/withdrawal, concurrent durable limits, rollback, partial provider-sync failure, recipient isolation, simultaneous campaign prepare/send and persisted ambiguous-operation stops. Its provider boundary is a test double: no test calls Resend or sends mail. Migration prefers private `DATABASE_URL_UNPOOLED` or `POSTGRES_URL_NON_POOLING` when available and otherwise uses the existing URL inside one transaction. Runtime, migration and database tests explicitly set `sslmode=verify-full` for genuine Neon hosts, preserving certificate and hostname checks instead of depending on legacy driver aliases. Local CI URLs keep their existing SSL settings.

Service dependency audit currently reports zero findings. The same-major Zod override replaces a vulnerable transitive pin in `@vercel/cli-config`; keep the lockfile and retest upgrades. This is separate from the static site's dependency audit.

## Owner deployment sequence

1. Use this directory as the root of the dedicated Vercel project `charitology-mail`, with Node `24.x`. Keep `.vercel/` and real environment files private. The public static Astro build stays on GitHub Pages.
2. Set private variables from `.env.example`, including `RESEND_SUBJECT_ID` for the stable authorized server identity; it is never accepted from a browser. Generate independent random secrets of at least 32 characters for `NEWSLETTER_ADMIN_TOKEN`, `NEWSLETTER_RATE_SECRET` and `CRON_SECRET`. Use the pooled `DATABASE_URL` for requests. Vercel supplies deployment OIDC for Connect; locally pulled OIDC expires. Never print credential values.
3. Run migration deliberately. Resolve the existing Resend domain allowance, add and verify `charitology.org` with its exact DNS records, and set `RESEND_DOMAIN_ID`. Preserve existing website and mail DNS. Check replies to `hello@charitology.org`. Disable open and click tracking on this dedicated domain: the service requires both actual API values to be false and refuses sending if either is enabled or unknown.
4. Run `node --env-file=.env.local scripts/setup-provider.mjs --create-preferences`. This creates/reuses the dedicated topic and segment, printing only their nonsecret IDs; it sends nothing. Set `RESEND_TOPIC_ID` and `RESEND_SEGMENT_ID` in Vercel. The topic must have `default_subscription=opt_out`, which requires explicit opt-in. Duplicate/paginated ambiguity or a wrong existing default stops setup. Inspect the provider after an ambiguous create before rerunning.
5. Deploy, attach `mail.charitology.org` and verify HTTPS, `/api/health`, `/privacy`, `/confirm` and `/unsubscribe`. Health checks database schema access and reports configuration flags; it does not prove inbox delivery. Leave `NEWSLETTER_SEND_ENABLED=false` until the actual sender is verified.
6. Configure a Resend webhook at `/api/webhook`, privately set `RESEND_WEBHOOK_SECRET`, and subscribe to supported delivery, bounce, complaint, suppression, `contact.created`, `contact.updated` and `contact.topics.updated` events. Verify real signed delivery. Event IDs are durably deduplicated; an unknown event is ignored. A signed `contact.created` may opportunistically resume only an existing confirmed pending activation; it never creates consent or sends mail. Resend documents that CSV imports do not emit these events, so daily maintenance and authenticated reconciliation provide independent recovery.
7. Keep `NEWSLETTER_TEST_ONLY=true`, privately set `NEWSLETTER_TEST_RECIPIENT`, then enable sending. Submit the real public form for that address. Open its email and press Confirm; GET alone must leave it pending. Confirmed contacts join only the dedicated segment and explicitly opt into its topic. Global unsubscribe and suppression are preserved.
8. Inspect protected preview/status, prepare the first native draft, inspect both formats and recipient scope, then deliberately send to the authorized controlled recipient. Verify actual inbox sender/body/plain text/postal footer/source links/native unsubscribe and future-send exclusion. Disable controlled-test mode only after the owner authorizes normal confirmed-subscriber operation.

Sender: `Charitology <hello@charitology.org>`. Reply address: `hello@charitology.org`. Postal footer: `938 Peacock Station Rd, McLean, VA 22102`. These are owner-supplied details, not legal certification or a claim that a funded institution exists.

## Public contract

- `POST /api/subscribe`: FormData, URL-encoded form or JSON with `email`, explicit `consent=yes`, and empty `website`. `Accept: application/json` gets `{ok,message}`; ordinary form posts get readable HTML. New, existing, suppressed, rate-limited and ineligible test addresses receive the same generic accepted message. Acceptance does not prove delivery. Provider rejection remains a private status record.
- Subscribe CORS permits exact origins from `NEWSLETTER_ALLOWED_ORIGINS`, defaulting to `https://charitology.org`. Add `http://127.0.0.1:4333` explicitly for local tests. No cookies are used.
- `GET /confirm?token=…` is a read-only explanation and POST form. POST atomically consumes a single-use token, records consent and requests provider preference sync. Its `no-referrer` form may submit an opaque `Origin: null`; confirmation accepts that literal value, an absent Origin or the exact service origin because the single-use bearer token authorizes the action. Other explicit origins are rejected. Signup and admin origin checks remain unchanged. Tokens contain 32 random bytes; only SHA-256 hashes enter Postgres. Expiry is 24 hours; a replacement invalidates its predecessor.
- `GET /unsubscribe?token=…` is read-only. POST records durable withdrawal before preference synchronization. The query token plus URL-encoded `List-Unsubscribe=One-Click` body is supported for cancellation in signup mail. Native Broadcasts use Resend's native unsubscribe link and preferences.
- `/privacy` explains storage and retention. Token pages use `no-store`, `no-referrer`, no-index and a restrictive content policy. Keep hosting logs private and add no analytics to these pages.

Consent copy version `charitology-letter-2026-10-26-v1`: “I want to receive The Charitology Letter by email. I can unsubscribe whenever I choose.” It matches the public checkbox.

Bodies are capped at 16 KiB, signed webhooks at 64 KiB. Email input is bounded ASCII syntax. Default durable limits: one request/address/15 minutes, eight/IP/hour, 50/day overall. Limit keys store secret-key hashes, not raw IPs. The trusted Vercel edge IP header is used, never arbitrary `x-forwarded-for`; local requests share an unknown bucket.

## Private operation

All admin routes require `Authorization: Bearer <NEWSLETTER_ADMIN_TOKEN>`. Use a private client reading its environment, never a command containing the secret value or a public browser bundle.

| Route                                | Action                                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `GET /api/admin/status`              | Counts and campaign states; no subscriber export                                                       |
| `GET /api/admin/readiness`           | Verified sender, tracking and topic/segment readiness; bounded error class/code/status only            |
| `GET /api/admin/preview`             | Edition 1 HTML/text, subject and SHA-256 content hash                                                  |
| `POST /api/admin/reconcile`          | Retry at most 20 pending preference updates; stop on provider error                                    |
| `POST /api/admin/cleanup`            | Remove expired limits, old pending requests/confirmation tokens and old webhook IDs                    |
| `GET /api/cron/maintenance`          | Cleanup, then guarded bounded preference recovery when enabled/ready; independent `CRON_SECRET` bearer |
| `POST /api/admin/campaign/prepare`   | Edition 1 alias; fresh work also requires the exact prepare-phase `reviewId`/`reviewHash`              |
| `POST /api/admin/campaign/send`      | Edition 1 alias; exact fresh send-phase proof and `confirm=SEND THIS REVIEWED ISSUE`                   |
| `POST /api/admin/campaign/reconcile` | Read saved provider status; never resend                                                               |

### Fixed issue publications and operational review

The R5 implementation adds an immutable service-root registry under `editions/`. It preserves the exact Edition 1 HTML, plain text and ordered content hash. Its public publication binding is generated from the fixed public registry, never supplied by an operator request. New issues require an explicitly selected fixed Letter edition; the initial capture registers no new send. Public publication, editorial labels and operational acknowledgement do not establish independent human review or delivery.

Generation is a root/build task after the root dependencies are installed. It does not run in a deployed Function. Use an explicit selection file with `{ "format": "charitology-mail-selection", "version": 1, "selections": [{ "publicationId": "letter-edition-one-preserved", "issueId": "edition-1" }] }`:

```sh
# From the repository root. Preview only; no provider or database access.
node services/newsletter/scripts/generate-editions.mjs --select-file /private/path/selection.json
# After inspecting that exact preview, append its immutable files.
node services/newsletter/scripts/generate-editions.mjs --select-file /private/path/selection.json --write --review-hash <reviewed-hash>
node services/newsletter/scripts/generate-editions.mjs --select-file /private/path/selection.json --check
node services/newsletter/scripts/check-editions-generation.mjs
```

`registry.json` is the only changing index. Existing issue and lineage blobs must remain byte-identical. Generation validates the complete previous closure and rechecks it before writing. An interrupted local file write requires inspection; do not remove historical blobs to force a new preview. The runtime has no dependency on the public source tree. `vercel.json` explicitly includes `editions/**` in the Node Function; release verification must inspect the actual packaged files.

| Route                                       | Exact purpose                                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `GET /api/admin/issues?cursor=…`            | Up to 20 safe metadata/state rows; optional returned cursor only                                                    |
| `GET /api/admin/issues/:id/preview`         | Fixed content and public/content hashes, available when sending is disabled                                         |
| `POST /api/admin/issues/:id/review-preview` | JSON `{phase,contentHash}`; inspect current issue, audience and, for send, exact saved native draft                 |
| `POST /api/admin/issues/:id/review`         | JSON `{phase,previewHash,previewToken,contentHash,acknowledgement}`; persist a proof only if recomputed facts match |
| `POST /api/admin/issues/:id/prepare`        | JSON `{contentHash,reviewId,reviewHash}`; consume a prepare proof before one unsent native create                   |
| `POST /api/admin/issues/:id/send`           | Same fields plus `confirm:"SEND THIS REVIEWED ISSUE"`; consume a separate send proof before one native send         |
| `POST /api/admin/issues/:id/reconcile`      | Empty JSON object or empty body; observe only the already saved native ID                                           |

The acknowledgement is exactly `I CHECKED THIS EXACT ISSUE AND INTENDED NEWSLETTER AUDIENCE`. The signed transient token expires after 15 minutes, contains hashes/counts rather than recipient addresses and is not a send capability. Its durable proof is bound to the bearer instance, phase, registered content, full registry, transport and current consent-generation audience. Audience or registry changes require a fresh preview. A shared bearer identifies operational access; it does not identify a named reviewer. Provider changes after the last read remain a race; native preferences and suppression still apply.

All issue requests retain the existing bearer and exact configured Origin rules, private/no-store headers and a 16 KiB body bound. Strict JSON rejects duplicate keys and malformed UTF-8. Only one exact harmless hosting `path` capture is tolerated; private query values are rejected. Hourly limits are 120 new reads, 20 review/prepare/send commands and a separate 20 reconciliations, overall and per bearer-instance hash. At most 20 live unconsumed proofs and 2 MiB of actual proof-row bytes are admitted. Each creating campaign reserves 8 KiB within a separate 2 MiB campaign-row bound so final outcome recording does not depend on new quota.

Checkpoint consumption and the creating/sending state commit together before the single native call. Existing accepted or uncertain history is retained even when sending is disabled. Correction ancestry crosses non-mailed intermediate editions; a recorded uncertain ancestor stops a new correction attempt. Reconciliation updates observations only. It cannot adopt an unknown native create, reset a stop, reauthorize a send or prove that recipients read the issue. Additive migration preserves legacy nullable evidence; it never invents review or attempt timestamps. Duplicate saved native IDs stop migration for private inspection.

Provider credential, fetch and streaming reads have an 8-second ceiling per operation inside a shared 45-second request deadline. Success bodies are at most 2 MiB, errors 16 KiB and native membership pages 512 KiB each, at most 30 pages of 100 unique IDs. Malformed or ambiguous responses stop the checkpoint without another call. The [R5 acceptance record](../../docs/PUBLICATION_EDITIONS_ACCEPTANCE.md) records the completed additive production migration, exact three-file local Function bundle, deployed strict registry/preview checks and retained accepted-issue operations. The provider API does not expose a downloadable physical lambda archive, so that physical hash check used a standalone build of the same service source. The exact tested production stage `dpl_Fq3m5MTPypeyg6aoPMNijNUoEZEG` is now live; no new issue, operational proof or mail send was created. Future fresh draft/send operations require their own deliberate acceptance; preserved historical timestamps stay null.

Readiness is a private operational check. It does not create a subscriber, send mail or prove inbox delivery. A production Connect grant must work in the deployed service; a successful local token request alone is insufficient. After a failed signup readiness check, respect the address request limit before retrying.

The Vercel cron runs daily at 06:00 UTC with its independent `CRON_SECRET`; verify the deployed cron succeeds. It cleans up first, then recovers at most 20 pending preference/import records only when sending is enabled and the actual sender/tracking/topic/segment readiness checks pass. A shared 45-second deadline bounds credential, provider and database work, leaving room within the 60-second function for connection/rollback cleanup. Individual failures do not stop later rows within the budget; failure or budget exhaustion returns 503 for operational review. It never prepares or sends a campaign. Disabled sending performs cleanup only. Pending requests are removed after seven days when cleanup runs, rate keys after two days, webhook IDs after 90 days. Consent and withdrawal evidence remain private; deletion must retain enough suppression information to honor withdrawal.

Prepare/send check the verified sender, topic default/name, segment name, pending-sync count, exact segment membership against private confirmed consent and the controlled-recipient gate. Send compares native draft HTML, text, subject, sender, reply address and topic/segment to the reviewed edition. Segment counts are not delivery counts: native preferences and suppression still filter delivery.

Native Broadcast creation/send have no documented idempotency guarantee. Committed intent precedes these calls; a nonblocking transaction-scoped advisory lock works through Neon's pooler. Competing preference/campaign requests fail busy and can be retried without occupying the connection pool while a winner needs an intent-write connection. `creating`, `create_unknown`, `sending` or `send_unknown` is a deliberate stop after a crash/ambiguous response. Never delete/reset such a record to blindly retry. Inspect provider drafts/status and delivery evidence first. Reconcile reports status without authorizing a resend. Each edition has one campaign record; a later issue needs a newly reviewed edition.

Only confirmed requests create provider Contacts. Ordinary `POST /contacts` is never used: actual provider testing showed that an email-only duplicate upsert resets a global unsubscribe. Instead a one-address native CSV import uses explicit `on_conflict=skip`, no memberships/preferences and a saved job ID/status. Real no-send contract testing confirmed both new creation and preservation of an existing true global unsubscribe. Sync checks the saved job/contact up to four times; asynchronous imports stay pending and resume through daily bounded maintenance or authenticated reconciliation. An ambiguous import submission can be retried only through the same skip-existing path, which may create another import job but never intentionally upserts a contact. New-contact import fails closed if any unrelated Topic has an opt-in or unknown default. Sync changes only the dedicated topic/segment and never resets a global unsubscribe, clears suppression or edits another topic. The shared team still has global Contacts/preferences; unrelated publications must use their own consented segments.

Each deliberate consent generation gets at most one Topic opt-in attempt, checkpointed before its provider call. Topic PATCH uses the top-level array required by the [HTTP contract](https://resend.com/docs/api-reference/contacts/update-contact-topics), with only the configured Topic and requested preference; the SDK's object wrapper is not the wire body. A bounded live opt-out contract check confirmed this shape. The request contains no global unsubscribe flag. A failed segment-add retry reads current native Topic state and preserves any opt-out. If the opt-in call was ambiguous and the native state is opt-out or unknown, activation stops; a new deliberate signup/confirmation is required. A mere new pending request never creates another opt-in authorization. Signed native Topic opt-outs become durable withdrawals. A valid event emitted before a newer DOI is ignored; an unparseable matching opt-out timestamp fails closed. Provider APIs offer no documented atomic preference version/CAS, so this uses their event emission timestamps and native preference filtering without claiming a stronger global ordering guarantee. Busy unsubscribe/webhook requests receive failure and need retry; already queued mail may remain in transit.

Withdrawal/blocked recovery reads the dedicated Topic's current preference and skips PATCH when it is already `opt_out`, then removes only the dedicated segment membership and clears the durable pending flag. Actual provider testing found that even an unchanged Topic PATCH emits another preference webhook; skipping that redundant mutation prevents an opt-out feedback loop. Failed reads or segment cleanup leave recovery pending. The provider-wide unsubscribe flag is never reset.

## Private Charity OS transactional relay

`POST /api/system/os-mail` is a server-to-server relay for the shared OS. Configure a separate random `OS_MAIL_RELAY_SECRET` of at least 32 characters and `OS_ORIGIN` (default `https://os.charitology.org`). Never expose this secret to a browser or reuse the newsletter admin/cron secret. Run the idempotent schema migration before deploying the route; it adds only `newsletter_os_mail_intents`. The existing Connect grant must work in production, the configured Charitology sender must be verified and open/click tracking must both be false. System mail is enabled by the separate relay secret and does not depend on the newsletter campaign flag or controlled-recipient flag.

Send `Authorization: Bearer <OS_MAIL_RELAY_SECRET>`, `Content-Type: application/json` and a unique `Idempotency-Key` of 1–128 letters, digits, dots, underscores, colons or hyphens. Do not include an Origin header. The legacy JSON body is `{purpose,to,url,organizationName?,title?,message?}`. Legacy purpose is exactly `login`, `invitation` or `reminder`; `to` is one address. Login URLs use the exact OS origin and `/auth/confirm`; invitations use `/invite`; reminders use `/app` or its subpaths. Embedded credentials and fragments are refused. Production origins require HTTPS; explicit loopback HTTP with a port is permitted only outside production. URLs are capped at 2,000 characters, organization/title at 180 and reminder text at 1,000; the whole request is capped at 16 KiB.

Authentication links and invitations use fixed operational copy. Arbitrary message text is rendered only for reminders, with HTML escaping and a plain-text alternative. Every message uses the existing Charitology sender and one transactional `/emails` send; it does not create/update a subscriber, Contact, Topic, Segment or Broadcast. No email address or bearer URL is persisted in the relay intent: payload and recipient use keyed hashes, while the idempotency key is hashed. Neither private content nor provider errors are logged.

The database commits one intent before requesting delivery. Exact accepted retries return 200 with `{ok:true,accepted:true,duplicate:true}`; the initial provider acceptance returns 202 with duplicate false. Acceptance is not proof of inbox delivery. Conflicting payloads or an in-progress/ambiguous previous attempt return 409 and are never blindly resent. Definitive failures return 503; request a fresh user action and key instead of resetting the old intent. A provider timeout or uncertain database completion leaves a durable stop. Native transactional-send idempotence uses the same hashed key as an additional protection, while the private intent is retained beyond the provider's 24-hour cache. Reservation uses a nonblocking transaction lock per key; duplicate callers cannot hold pooled connections waiting on the unique insert. Pool exhaustion returns 503 before a provider attempt and does not create a false acceptance.

Separate durable OS limits are 200 new attempts/day overall and 10/hour per recipient; duplicate accepted requests do not consume another attempt. Limit responses return 429. Failed readiness/send attempts retain their intent and consumed limit. The OS authentication API must also enforce its own public request limits and single-use token expiry. Relay acceptance does not authorize invitation membership, verify a login token or execute a task; those are OS server responsibilities.

`test/os-mail.test.mjs` checks authorization, exact origins/paths, request bounds, escaping, single-recipient transport, idempotence, ambiguous failure and isolation from newsletter flows. `test-db/os-mail.test.mjs` exercises actual isolated Postgres concurrency at the three-connection pool capacity, durable limits, idempotent migration, accepted-state preservation and intentional pool exhaustion with a mocked provider. It sends no emails and does not touch production records. These are correctness and failure-recovery checks, not a throughput benchmark.

### Participation updates: separate delivery consent and gates

The relay also implements the fixed participation purpose described in [the participation delivery contract](../../docs/PARTICIPATION_DELIVERY_PLAN.md). It accepts exactly `{purpose:"participation",to,url}`, with one recipient and the exact clean `${OS_ORIGIN}/participant` URL. Custom organization/title/message fields, alternate paths, queries and fragments are rejected. HTML and plain text contain a fixed generic portal notice, the Charitology sender/reply address and postal footer. They contain no request receipt, sign-in capability, occurrence details or attendance claim. This is operational mail; it neither subscribes anyone to marketing nor changes newsletter Contacts, Topics, Segments, Broadcasts or global preferences.

Participation delivery defaults off. Set `OS_PARTICIPATION_DELIVERY_ENABLED=true` deliberately; retain `OS_PARTICIPATION_TEST_ONLY=true` and the private `OS_PARTICIPATION_TEST_RECIPIENT` for controlled testing. These gates are independent of `NEWSLETTER_SEND_ENABLED` and the newsletter test recipient. The existing server bearer, authorized deployed Connect subject, verified sender with both tracking flags false, and exact-recipient suppression read remain required. Only the fixed suppression endpoint's observed HTTP404 `{name:"not_found",message:"Suppression not found"}` means absence. Other errors, malformed responses and uncertain permissions stop a new attempt; the relay never removes suppression or changes a Contact to bypass it. The OS must independently enforce current own-link identity, fresh specific email consent, scoped activation and the final dispatch check. Relay acceptance grants none of those permissions.

Before release, rerun the idempotent migration. It explicitly widens the populated purpose/state CHECKs and adds `attempted_at`, `correlation_hash`, `safe_code`, bounded `provider_facts` and participation-specific constraints/indexes. Legacy outcomes remain compatible. New participation attempts charge the existing200/day overall and10/recipient/hour durable send limits once at the committed attempt checkpoint. A readiness failure before that checkpoint can retain an internal `preflight` intent without consuming send quota. Only an explicit **send response** `state:"unavailable",safeCode:"preflight_unavailable"` proves no possible attempt and allows the identical key/payload to be reclaimed. Lost responses, creating/missing/unknown status, conflicts, rate failures or status outages never permit a fresh key or blind resend. Existing possible-attempt outcomes are checked before enablement gates, and keyed stops remain durable beyond the provider's24-hour idempotency cache.

`POST /api/system/os-mail/status` uses the same bearer and rejects any Origin header. Its body is exactly `{idempotencyKey}`; the key never belongs in a URL. The endpoint tolerates only one exact harmless Vercel `path` rewrite capture and rejects all other/wrong/duplicate query fields. Authenticated reads have their own durable60/minute overall cap and do not consume send quota. Both new-purpose send and status outcomes contain only `ok`, `state`, `safeCode`, `providerEventAt`; no recipient, provider ID, token or payload is returned. A never-seen status key returns unknown, which is not permission to send. Status may recover validated provider facts without resending; retrieval creation time and poll time are never presented as delivery-event time. Accepted by the provider and delivered to a receiving mail server do not prove inbox placement or reading.

The existing `/api/webhook` verifies the raw body with Svix headers before parsing and atomically commits deduplication plus newsletter/OS effects. Bound provider IDs or an opaque keyed correlation tag may attach only to an existing attempted participation intent with the exact recipient/sender/subject binding. Unmatched shared-team callbacks cannot create consent, a request or mail. Bounded delivery, bounce, complaint and suppression facts survive duplicate/reordered callbacks; later blocking evidence is retained after delivery. Provider error bodies and raw shared-team events are not exposed or retained as a new recipient list.

`test/participation-mail.test.mjs` and `test-db/participation-mail.test.mjs` cover these boundaries, including populated legacy migration, same-key races, preflight-only retry, ambiguous stops, bounded provider responses, signed early feedback and atomic callback rollback. Their recipients are synthetic and their provider is a test double. These checks do not establish deployed routing, current provider permissions, real tag/callback compatibility or inbox delivery. The published runtime passed those staged checks and a separate actual controlled owned-inbox test; the final general-recipient deployment and exact proof limits are in [the delivery acceptance record](../../docs/PARTICIPATION_DELIVERY.md). Old paused history is never automatically flushed.

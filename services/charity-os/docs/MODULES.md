# Charity OS module contracts

Implementation contract · October 26, 2026 · AI-assisted. The registry implements 26 typed module models and validation. Authentication, persistence, delivery, connectors and deployment have their own acceptance checks. A schema does not establish that an external system has been integrated or that an organization has tested the workflow.

Charitology studies the system that directs generosity. Program design connects resources, work, intended change, evidence and review. Depth remains an optional descriptive hypothesis from 0 through 4. The workspace does not rate named charities or turn an activity count into a causal impact claim.

## One engine, distinct domains

`../lib/modules.mjs` exports plain JSON metadata in `MODULES` and `MODULE_MAP`. Every module has its own fields, record kinds, states, transition rules, read/write/approval/export roles, calendar field, invariants and fictional example. The API and browser use the same definitions. Unknown fields are rejected rather than stored as invisible data.

The API owns an envelope containing opaque `id`, `orgId`, `moduleId`, `revision`, `status`, `ownerId`, creator/update metadata and `accessScope`. Domain fields live in `data`; they cannot change an envelope or grant access. An organization profile is not an authentication membership. Fields such as `programId`, a linked agreement and record type retain meaning across the module boundary.

Use server-generated IDs before validation. Every mutation takes the expected revision. Resolve and lock the organization membership, access scope and relevant records inside the same database transaction. Serialize capacity, allocation and uniqueness checks with the write: two concurrent requests must not both consume the final place or final budget amount. A pure validator alone cannot provide transaction isolation.

`validateRecord(moduleId,data,{records,recordId,orgId,status,previous})` returns a fresh normalized object or throws `ModuleValidationError`, with HTTP status 422 and structured `issues: [{field,message}]`. `records` accepts an array or Map of envelopes. Pass the complete relevant organization dataset, including existing approved allocations and active assignments. A linked ID without reference context is refused. The server must enforce program/team scope before allowing either a link or a read; a matching organization is not sufficient authorization.

## Types and missingness

The supported metadata types are `text`, `textarea`, `integer`, `number`, `select`, `boolean`, `date`, `datetime`, `timezone`, `money`, `reference` and `references`. Optional unknown values normalize to `null`; explicit numeric zero and boolean false remain intact. Inputs are bounded by field and a 64,000-byte normalized record limit.

Money is `{minor,currency,precision}`, where minor is a safe integer or null. A whole unknown money field may also be null. The explicit supported precision table is exported as `CURRENCIES`: USD, EUR, GBP, CAD, AUD, NZD and CHF use 2; JPY uses 0; KWD uses 3. Other currencies need a reviewed table extension before use. Only explicitly signed variance fields permit negative amounts. `summarizeMoney` groups totals by currency and precision and reports missing amounts separately. No implicit exchange rate or unknown-to-zero conversion occurs. Allocation percentage arithmetic uses integer basis points and BigInt intermediate arithmetic, rounded to the nearest minor unit.

Dates use real `YYYY-MM-DD` values from 1900 through 2200. Instants include seconds and an explicit offset, paired with a recognized IANA zone. The offset must agree with that zone at that instant, including daylight-saving time. Start/end comparisons use instants so overnight shifts work. Never infer an offset from the browser's machine or reinterpret a date as midnight UTC.

HTTPS references cannot contain embedded credentials. Source/external-ID pairs are unique within a module. Identifiers are opaque codes, not secrets. There is no credential field in a mapping or connector record.

## The 26 modules

| Module ID | Concrete records and relationships | Workflow and checks |
| --- | --- | --- |
| `organization` | Profiles, teams and access-review records; mission, jurisdiction, zone, currency and administrator handover | Draft → review → approved → archived. Only owner/admin write. Actual invitations, roles and revocation use the access API. |
| `programs` | Programs, system maps and assumptions; community context, mechanism, descriptive depth and evidence label | Draft → review → approved → active → review due → closed. Source and assumptions remain explicit. |
| `projects` | Projects, tasks and milestones linked to programs, parent projects and dependencies | Planned → ready → active → review → done. Cycles/self-links are refused; prerequisites must be done before completion. |
| `grant-seeking` | Opportunities/applications linked to funder contacts, programs and document versions; eligibility, requested amount, deadline and submission reference | Prospect → drafting → review → approved → submitted → decided. Submission needs eligibility, version, reference and immutable approved snapshot. No funder submission is performed. |
| `grant-delivery` | Agreements, restrictions, reports and amendments linked to applications and parent agreements | Draft → review → approved → active → reporting → closed. Restricted awards need purpose and a matching restriction code; award/commitment/spending currencies agree. Overruns need an explanation rather than disappearing. |
| `finance` | Budgets, allocations, scenarios and actual references; parent budget, agreement, program, money and basis points | Draft → review → approved → active → reconciled → closed. Approved child totals cannot exceed parent/award caps; currency, precision, program and restriction codes agree. Parent budget reductions cannot invalidate approved allocations silently. |
| `accounting` | External ledger references, reconciliation and aggregate payroll summaries | Draft → review → approved → reconciled → closed. Reconciliation needs source identity and an explicit result. No bank credentials, individual payroll, ledger posting, tax filing or statutory certification. |
| `contacts` | Organization/person references and relationships; optional email, operational preference and source identity | Draft → verified → active → archived. Offline contacts are valid. Duplicate external mappings are refused; beneficiary histories are excluded. |
| `fundraising` | Campaigns, pledges, external gift references and acknowledgments linked to donors/programs | Planned → review → approved → active → reconciled → acknowledged. Pledges are separate from receipts; reconciled gifts need receipt/date and restrictions. No funds move or tax receipt is issued. |
| `memberships` | Membership types, chapters, members and renewals; periods, dues references and directory consent | Draft → review → approved → active → renewal due → expired. Chapter kind and date ordering are checked; externally verified dues need a reference. Directory publication is a separate permission. |
| `volunteers` | Profiles, shifts, assignments and attendance; contact, program, training reference and explicit instants | Draft → review → approved → open → assigned → completed. Capacity, duplicate bookings, overlapping assignments and attendance duration are checked. Capacity/time edits recheck existing assignments. |
| `events` | Sessions, registrations and attendance; program/contact, capacity and access-coordination status | Draft → review → approved → scheduled → open → completed. Duplicate registrations and capacity excess are refused; walk-ins remain distinct from registrations. No private medical access notes. |
| `communications` | Purpose-specific consent, templates, campaign references and delivery references | Draft → review → approved → active → withdrawn → archived. Opt-in needs purpose, instant and evidence; suppression prevents active sending authorization. Template approval does not dispatch mail. |
| `forms` | Versioned non-sensitive question schemas and aggregate response batches | Draft → review → approved → published → closed. Published forms require bounded schema, version, purpose, retention date and frozen approval. Individual intake answers are not stored in these records. |
| `casework` | Referral/request/appointment/service-summary coordination codes and external specialist references | Requested → triaged → review → approved → referred → completed. Title must equal the opaque coordination code. Completion needs an external reference and recorded/not-required consent. No narrative case field exists. |
| `outcomes` | Indicators, observations and harms linked to programs; value, unit, period, denominator, geography, method, evidence and limitations | Draft → review → approved → included → superseded. Null differs from zero; linked units agree; rates need a positive denominator; source-linked claims need a source. |
| `feedback` | Aggregate themes, summaries and responses with channel, permission and response deadline | Received → triaged → review → approved → responded → published → closed. Public output needs explicit permission, de-identified summary, response/change and snapshot. |
| `evaluation` | Questions, protocols, reviews and decisions linked to outcome records | Draft → review → approved → registered → analyzing → decided → follow-up → closed. Registration declares a question/method; decisions include uncertainty and follow-up. Unknown evidence is allowed. |
| `reporting` | Board/funder/public reports and templates linked to agreement, outcome and finance sources | Draft → review → approved → frozen → issued → superseded. Frozen outputs require period, summary, missingness and immutable source revisions. Public visibility in data is not publication permission. |
| `governance` | Meetings, decisions, conflicts, delegation and policy; votes, quorum, recusal and review | Draft → agenda → review → approved → recorded → superseded. Known votes satisfy quorum; declared conflicts need a recusal reference; recorded output is snapshotted. |
| `documents` | Documents, versions, retention and handover knowledge; external private link, checksum, classification and hold | Draft → review → approved → archived → deletion requested. Parent/version pairs are unique; a retention hold prevents deletion approval. External files have their own audited storage operations. |
| `safeguarding` | Training/screening status and escalation-route references | Pending → review → approved → current → due → expired. Current status requires date and verification reference. Specialist systems retain criminal/medical/allegation reports. |
| `assets` | Equipment, stock, procurement and in-kind references linked to programs/suppliers | Requested → review → approved → ordered → received → assigned → disposed. Received stock needs known quantity, date and receipt; no supplier payment or order is placed. |
| `resources` | Tool/benefit eligibility and renewal reviews with current terms, cost and enrollment reference | Discovered → review → approved → applied → active → expired. Active enrollment requires eligible status, source and confirmation. A listing does not itself enroll a charity. |
| `integrations` | Connectors, mappings, imports, sync runs and conflicts; field ownership, source checksum and row counts | Draft → mapped → preview → approved → running → completed → closed. Import approval needs a reviewed preview; input equals accepted + rejected + skipped. Secret/executable mapping values are excluded. |
| `administration` | Incidents, backups, restore tests, retention and cost limits | Planned → review → approved → running → verified → closed. Verified backups have reference/checksum; restore tests also reconcile known counts and record test instant. A cost limit never authorizes provisioning. |

Cancellation is available where declared in the registry. Cancelling a draft does not require completing its future operational milestones. Approved/frozen data must be corrected through a new revision and reason, preserving the original snapshot.

## Approval, ownership and snapshots

`modulePermissions(moduleId,role)` returns read, write, approve and export booleans. Supported roles are owner, admin, program lead, grants lead, finance reviewer, contributor, board reader and external reviewer, represented by the exported snake-case IDs. Ownership is an envelope assignment, not permission. Restricted casework/safeguarding excludes board and external readers; finance/contact/governance/administration have explicit role lists. Membership, program/team scope and revocation must still be checked for each request.

`validateTransition(moduleId,from,to,context)` checks a declared edge, role, persisted approval and required snapshot. Pass validated `data` in the context to check the target state's domain prerequisites too. Approval context is derived from the server's persisted approval, with `approved:true`, `approvalApproved:true` or `approval.status:'approved'`. Snapshot transitions require `snapshotApproved:true`. Never copy either flag from a request. Compare the approval's revision and content hash to the data being transitioned.

Independent approval is the default. When actor and owner are the same, approval fails unless an explicit server-side organization policy supplies `allowSelfApproval:true`. Invitations and role changes remain separately audited. Board/external readers must receive only approved snapshots within their assigned scope, not raw working or restricted records. Public publication is a distinct `publish` permission, with a preview and source review.

An immutable snapshot contains domain data, organization/module/record IDs, source revision, linked source IDs/revisions, content hash, approval identity/time and creation time. Corrections append a reason and new revision; exporting an old snapshot does not recalculate it using later source data. Do not place bearer tokens, private invitation URLs or sensitive text in audit events.

## Export, import and migration

The API should emit a versioned organization envelope containing the registry schema version, export instant, selected records, allowed snapshots and reconciliation counts. Include stable IDs and relationship targets, while enforcing the export permission and caller's exact data scope. CSV exports quote every cell and neutralize formula-like text; JSON is the lossless restore format. Unlike currencies remain separate. A scoped export is labeled partial and cannot claim to be a complete organization backup.

Import is a two-step operation. Parse and bound the upload, validate the envelope version, reject duplicate IDs and cross-tenant links, resolve collisions and preview every row and total before any write. Validate the merged candidate dataset, not rows against the old database one at a time: forward references, capacity and totals depend on the full import. Commit the approved preview/hash atomically with revision checks and an import journal. A rollback uses that journal and refuses to erase subsequent independent changes. User-supplied approvals, actor IDs, membership grants and audit history never become trusted server facts.

The existing local Charity OS export contains organization context, projects, grants, tasks and observations. Convert major-unit money using the local export's explicit currency and precision, refusing excess decimal precision instead of silently rounding. Preserve local IDs through an import mapping; link tasks to migrated projects. Local owner labels are descriptive text, not authenticated member IDs. Local statuses map into a draft/review workflow; they cannot establish approval. Keep the source file and a readable migration journal available to the organization.

## Verification

`exampleRecords(orgId)` creates 26 complete fictional drafts that pass the actual validator. It neither seeds production nor claims measured outcomes. `test/module-contracts.test.mjs` checks all module examples plus money missingness/precision/overflow, timezone and overnight behavior, dependency cycles, tenant links, budget and award caps, restrictions, volunteer capacity and duplicate bookings, measurement units/denominators, duplicate external mappings, unsafe URLs, row reconciliation and approval/snapshot roles.

These tests verify domain contracts. Full release acceptance also needs real authenticated multi-organization isolation, concurrent writes, revocation, scoped exports, immutable snapshot verification, migration preview/commit, independent restore, keyboard/mobile behavior and actual transactional delivery. The relevant workflow must expose failures and retain recoverable drafts instead of reporting success after a rejected write.
